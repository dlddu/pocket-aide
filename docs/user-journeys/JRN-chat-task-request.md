## 1. 서비스 개요 (참고)

PocketAide 채팅 탭은 긴 하나의 대화로 에이전트(부모 세션)에게 일을 맡기는 자리다. 부모는 맡은 일을 자기 **작업 원장**(슬롯 SQLite)에 적어 두고 관리한다. 넓은 창에서는 그 원장이 대화 오른쪽에 함께 보이므로, 사용자는 "무엇이 막혀 있는지"를 대화를 되짚지 않고 본다.

이 여정은 **본 다음에 말을 얹는** 흐름이다. 지금까지 그 말은 대화 메시지로만 보낼 수 있었고, 답이 쓰이는 중에는 보낼 수 없었다. 이제 요청은 그 작업의 원장에 저장되고, 부모가 다음 확인 때 접수한다.

## 2. 여정 정의

| 항목 | 내용 |
| --- | --- |
| 페르소나 | 자기 일을 에이전트에게 맡겨 둔 단독 사용자(개발자). 작업 원장의 상태 용어(검토 — 사람이 판단할 일 하나)를 읽을 수 있다 |
| 진입 맥락 | 넓은 화면(태블릿·펼친 폴더블·데스크톱 창)에서 채팅 탭을 보고 있다. 부모가 작업을 하나 이상 원장에 적어 두었다 |
| 트리거 | 패널에서 막힌·검토 대기 작업을 보고 "이건 이렇게 해 달라"고 말할 것이 생긴다. 또는 답이 쓰이는 중에 끼어들지 않고 지시를 남겨 두고 싶다 |
| 완료 기준 | (a) 요청이 그 작업의 원장에 저장되고 화면이 「저장됨 · 부모 확인 대기」로 말한다, 또는 (b) 저장할 수 없는 이유를 듣고 쓴 말을 잃지 않는다, 또는 (c) 패널에서 보기만 하고 남길 것이 없어 끝낸다 |
| 소요 시간 | 30초~2분 (읽기 + 한 문장) |

## 3. 단계별 상세

각 단계의 식별자는 안정적이다 — 문구가 바뀌어도 이 id는 유지한다.

### `STP-open-wide` 넓은 창에서 패널을 함께 보기

- **행동**: 채팅 탭을 넓은 창에서 연다(또는 접어 둔 패널을 헤더 토글로 펼친다).
- **터치포인트**: 대화 왼쪽 · 작업 패널 오른쪽 1:1, 헤더의 패널 토글.
- **감정**: "지금 뭐가 걸려 있나" — 확인하려는 상태.
- **페인포인트**: 좁은 창에는 패널이 없다(대화만). 창을 넓히거나 기기를 펼쳐야 한다.

### `STP-narrow-list` 칩과 완료 숨김으로 볼 것만 남기기

- **행동**: 상태 칩(검토·진행·…)을 눌러 좁히고, 필요하면 「완료 숨기기」를 켠다. 다시 누르면 전체로 돌아간다.
- **터치포인트**: 상태 칩(개수 포함), 완료 숨김 토글, 비었을 때의 되돌리기 칩.
- **감정**: 목록이 줄며 "손댈 것"만 남는 안도.
- **페인포인트**: 빈 목록이 "일이 없다"로 읽히면 오해다 — 화면은 숨김 때문인지, 그 상태가 없는 것인지, 원장이 비었는지를 구분해 말한다.

### `STP-open-task` 작업 하나로 들어가 원장 그대로 읽기

- **행동**: 작업 줄을 누른다. 같은 오른쪽 칸이 상세로 바뀐다.
- **터치포인트**: 작업 카드, 상세의 상태 배지·단계·사유·다음 행동·작업 ID, 뒤로.
- **감정**: "왜 막혔는지" 확인.
- **페인포인트**: 원장에 사유가 적혀 있지 않을 때가 있다 — 화면은 빈칸이 아니라 「원장에 적혀 있지 않아요」로 말한다.

### `STP-compose-request` 추천을 고르거나 직접 쓰기

- **행동**: 추천을 눌러 요청 칸을 채우거나, 직접 쓴다. 추천은 **보내지 않고 채운다**.
- **터치포인트**: 추천 목록(원장 인용), 요청 입력 칸.
- **감정**: 나갈 문장을 내가 읽고 고칠 수 있다는 통제감.
- **페인포인트**: 추천이 원장에 없는 사유를 지어내면 신뢰가 깨진다 — 없으면 "적혀 있지 않다"고 쓰고 묻는 문장을 준다.

### `STP-store-request` 「요청 등록」으로 원장에 남기기

- **행동**: 「요청 등록」을 누른다. 답이 쓰이는 중에도 눌릴 수 있다.
- **터치포인트**: 등록 버튼, 저장 중 표시, 결과 문구.
- **감정**: 끼어들지 않고 지시를 남겼다는 안심.
- **페인포인트**: "보냈다"와 "처리됐다"가 섞이면 기다릴지 말지 알 수 없다 — 화면은 「요청 저장됨 · 부모 확인 대기」로만 말한다.

### `STP-see-waiting` 접수 전 요청과 그 상태를 확인하기

- **행동**: 상세에 남아 있거나 다시 들어와, 아직 접수되지 않은 요청 수를 본다.
- **터치포인트**: 「보낸 요청 · 확인 대기 n건」(원장이 센 값), 결과 대조 중인 건수.
- **감정**: 기다림의 근거가 화면에 있다.
- **페인포인트**: 부모가 접수·처리할 때까지는 수치만 바뀐다 — 즉시 응답을 기대하면 느리게 느껴진다.

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
| --- | --- | --- |
| 우회 경로 — 좁은 창 | 패널이 없어 이 여정은 시작되지 않는다. 대화로 말하거나 창을 넓힌다 | 해당 없음 |
| 우회 경로 — 보기만 하고 끝 | 칩·상세로 확인만 하고 요청을 남기지 않는다(완료 기준 (c)) | 해당 없음 |
| 실패 케이스 — 작업이 원장에서 사라짐(404) | 「이 작업이 원장에서 사라졌어요」. 상세가 닫히고 목록이 다시 그려진다 | `STP-narrow-list` |
| 실패 케이스 — 세션이 깨어 있지 않음(409) | 「채팅 세션이 깨어 있지 않아 저장하지 못했어요」. 쓴 말은 남고 같은 번호로 다시 저장한다 | `STP-store-request` |
| 실패 케이스 — 요청을 받지 않는 세션(501) | 「이 대화의 세션은 작업 요청을 받지 않아요」. 대화로 말하는 길은 그대로 있다 | `STP-compose-request` |
| 실패 케이스 — 네트워크·서버 오류 | 「요청을 저장하지 못했어요」. 초안·요청 번호 유지, 「다시 저장하기」 | `STP-store-request` |
| 중복 방지 — 같은 요청을 두 번 누름·응답을 못 본 채 재시도 | 같은 요청 번호로 가므로 원장에는 한 건이고 화면은 「이미 저장된 요청이에요」로 말한다 | `STP-see-waiting` |
| 중도 이탈 — 다른 작업으로 이동·탭 이탈 | 요청 칸은 작업마다 비워지고(앞 작업의 말이 따라오지 않는다), 저장된 요청은 원장에 남는다 | `STP-open-task` |
| 접수 뒤 — 부모가 처리 중 죽음 | 부모 쪽 계약이 적힌 실행 의도로 대조한다(재실행이 아니라 확인). 사용자 화면에는 「결과 대조 중」으로 보인다 | `STP-see-waiting` |

## 5. 측정 지표

| 지표 | 정의 | 왜 보는가 |
| --- | --- | --- |
| 요청 저장 성공률 | 「요청 등록」 탭 대비 201/200 비율 | 저장 경로가 실제로 쓰이는지, 실패가 특정 사유에 몰리는지 |
| 중복 저장 건수 | 같은 요청 번호로 두 번 이상 들어온 비율(= `replayed`) | 재시도가 한 건으로 남는지 — 0이 아니어도 정상이고, **원장 행 수**가 늘지 않는 것이 기준 |
| 접수까지 걸린 시간 | 저장 시각 → 부모가 claim 한 시각 | "부모 확인 대기"가 사용자에게 얼마나 긴 기다림인지 |
| 미접수 누적 | 작업별 `pending` 건수의 분포 | 요청이 쌓이기만 하는 작업이 있는지(부모 발견 누락 신호) |
