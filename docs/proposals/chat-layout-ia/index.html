채팅 탭 화면 구조 — 디자인 제안 3안 비교

대화와 작업 원장을 어디서 진입·전환하는지가 서로 다른 3개의 정보 구조. 기본 채팅 · 확장(좁은 폭) · 확장(넓은 폭)을 각각 눌러 볼 수 있다.

시안이다. 아래 모든 내용은 가상 데이터이고, 이 페이지는 네트워크를 전혀 쓰지 않는다 — 실제 작업 원장·세션·인증을 호출하지 않으며 어떤 메시지도 전송되지 않는다. 공식 목업(docs/mockups/)과 제품 문서를 대체하지 않는다. 채택 결정은 사용자 검토에 남긴다.

읽는 법

현재 main 에 구현돼 있다 제안 아직 열린 PR 의 계약이다
  • 제안 표시는 미병합 PR 의 계약이라서, 채택해도 그 PR 이 들어온 뒤에만 그려진다.

따라가 볼 동선

  • 입력창에 한 줄 쓰다가 멈춘다 (초안이 생긴다)
  • 원장으로 가서 작업 진행을 확인한다
  • 「검토」 작업을 열어 연결된 PR · 이미 결정된 것 · 아직 판단이 필요한 것 · 대안별 장단점과 최신 질문·선택지를 읽는다
  • 돌아가기로 대화에 복귀 — 쓰던 문장이 그대로 있는지 본다

현재 구현에서 확인한 것

  • 작업 원장은 넓은 폭 전용이다. 좁은 폭에는 패널도, 그걸 여는 토글도 그려지지 않는다 (ChatScreen.kt:336-337, 357-359, 450-452). 세 안은 모두 이 빈칸을 메우는 제안이다.
  • 넓은 폭은 1:1 분할 + 1dp 구분선이고, 보조 창은 좁은 폭에서 아예 올리지 않는다 (tokens.md §6.2). 접힌 창은 폴링도 하지 않는다 (ChatScreen.kt:342-344).
  • 분기는 기기가 아니라 창의 가용 폭 600dp로 한 번 판단한다 (tokens.md §6.1).
  • 「주고받은 내용」은 상세 맨 아래에 접혀 있고 펼칠 때만 읽는다 (#425, 머지됨).
  • 작업 상세의 요청·선택지는 대화로 보내지 않는다 (ChatTaskDetail.kt:471).
  • iOS 에는 작업 패널·분할이 아직 없다 (ios/ 에 해당 코드 없음) — 세 안 모두 iOS 는 신규 구현이다.

디자인 시스템을 넓혀야 하는 지점

  • components.md §9 Sheet 는 다짐 영역용 1종만 정의돼 있다(「확장 여지」). A안의 시트는 그 도출 규칙대로 AI 채팅 토큰으로 옮겨 그렸다 — backdrop 은 영역 ink 에 alpha, 본체는 영역 표면색, 핸들은 영역 --rule. 채택하면 §9 에 AI 채팅 변형을 먼저 등재해야 한다.
  • §4 FilterPills 의 활성 칩은 --soft 를 쓰는데 AI 채팅 라이트에는 --soft 가 없다(tokens.md §1.3). 여기서는 구현이 택한 ink alpha 를 따랐다 (ChatTaskPanel.kt) — 토큰이든 컴포넌트든 한쪽을 정해야 한다.
  • §6 의 Frame 은 393×852 하나뿐이다. 넓은 폭은 820dp 로 가정해 그렸고, 이 수치는 시스템에 없는 이 시안의 가정이다.
  • 기존 대비 문제 2건(세 안 공통이고 이 제안이 만든 것이 아니다): §7 의 비활성 탭 라벨 stone-400 은 흰 탭 바 위에서 2.5:1, §1.3 의 --sage 를 자기 12% 틴트 위에 올리면 3.26:1 로 둘 다 WCAG AA(4.5:1)에 못 미친다. 탭 라벨은 시스템에 충실하게 그대로 두었고(= 지금 앱도 이 대비다), 칩·배지는 읽히는 톤으로 바꾼 뒤 위에 그 예외를 적었다.
