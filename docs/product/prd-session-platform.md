# PRD: 세션 플랫폼 연동 (폰에서 Claude Code 세션 운용)

## 달성 가치
- **V9**: 개발 워크플로우 인지 부하 감소 — 진행 중인 에이전트 작업의 상태(active/idle/snapshot)와 출력을 별도 도구(SPA·데스크톱) 전환 없이 앱 안에서 파악하고, 세션을 생성·지시·재개·정리한다. 데스크톱 앞으로 돌아가 SPA를 여는 것 자체가 컨텍스트 스위칭 비용이므로, 폰에서 세션을 운용할 수 있게 하는 것이 그 비용을 제거한다.
- **V5**: 자연어 대화 기반 작업 처리 — 에이전트에게 보내는 지시가 명령어나 폼이 아니라 자연어 프롬프트이다.

> **가치 해석 노트**: `values.md`의 V9 설명은 현재 PR·CI 상태 확인(상태를 *받아보는* 축)을 중심으로 서술되어 있다. 본 PRD는 "자리 밖에서 작업을 *진행시킨다*"까지 V9의 가치명("개발 워크플로우 인지 부하 감소") 범위 안으로 읽는다. 이 해석이 의도와 다르면 V9 설명을 보강하거나 별도 가치를 신설해야 한다 — 아래 열린 질문 참조. 본 PRD는 가치 문서를 변경하지 않는다.

## 개요

PocketAide 백엔드가 [session-platform](https://github.com/dlddu/session-platform) 컨트롤 플레인의 **프록시**가 되어, iOS 앱이 기존 OIDC 세션만으로 `claude-code` 워크로드 세션의 **전체 라이프사이클**을 폰에서 수행한다.

```
iOS 앱 ──(OIDC Bearer)──► pocket-aide 백엔드 ──(클러스터 내부 DNS)──► session-platform
   pocket-aide.${PUBLIC_DOMAIN}      /api/sessions*        control-plane.session-platform.svc:80
                                                                    │
                                                              per-session pod (claude-code)
```

다루는 라이프사이클: **생성 → 프롬프트 전송 → 출력 이어보기 → 스냅샷 → 복원 → 삭제**.

이 PRD가 해결하려는 문제는 "에이전트에게 맡길 수 있는 작업인데 자리에 앉아 있어야만 시작·확인할 수 있다"는 제약이다. 세션은 pod로 격리되어 있고 idle 시 스냅샷으로 컴퓨트를 반납하므로, 폰에서 띄운 세션이 방치되어도 비용이 누적되지 않는다.

### 전제 (레포 확인 결과)

| 항목 | 확인된 사실 | 본 PRD에 미치는 영향 |
|------|-------------|---------------------|
| session-platform 인증 | OpenAPI 스펙에 인증 정의 없음 | 프록시가 **유일한 인증 경계** (AC1) |
| session-platform 노출 | `session-platform.${PRIVATE_DOMAIN}` + Traefik `allow-internal-only` | 공용 도메인 뒤의 프록시가 내부 전용 API를 외부에 잇게 됨 → 보안 검토 필요 (열린 질문) |
| 사용자 개념 | 없음. 세션은 전역 목록 | 소유권 매핑을 PocketAide가 보유 (AC2) |
| 워크로드 | `shell` / `claude-code`, 생성 시 고정·불변 | 앱은 `claude-code`만 생성 (AC3) |
| 모델 | 생성 시 고정·불변. `GET /config`가 기본값+카탈로그 제공 | 생성 화면에서만 선택 (AC4) |
| 스냅샷 | `CLAUDE_CODE_ARCHIVE_ENABLED` 게이트, 기본 off. off면 503 + pod 유지 | 실패가 아닌 "비활성" 안내 (AC8) |
| 출력 | append-only 버퍼, 서버 발급 바이트 커서, 누적 256 MiB 상한 | 커서 규약 준수 (AC7) |
| 쓰기 | 비동기 큐 등록. 1 MiB 초과 시 413 | 전송 ≠ 완료 (AC6) |

## 사용자 시나리오 (대표)

1. 퇴근길 지하철에서 앱을 연다 → 새 세션 생성 후 "이 레포 테스트 실패 원인 찾아줘" 프롬프트 전송 → 집 도착 후 출력 확인.
2. 회의 중 세션 목록을 확인한다 → 어제 세션이 `idle` 배지 → 열어서 프롬프트를 보내면 자동으로 `active` 승격되어 그대로 이어진다.
3. 일주일 전 세션이 `snapshot` 상태 → "복원" 탭 → 수십 초 뒤 이전 출력 이력이 그대로 이어지고 후속 프롬프트를 보낸다.
4. 긴 응답이 스트리밍되는 도중 앱을 백그라운드로 보냈다가 복귀 → 마지막 커서부터 중복·누락 없이 이어진다.
5. 끝난 작업의 세션을 삭제 → 확인 절차 후 pod가 회수되고 목록에서 사라진다.

## Acceptance Criteria

### AC1: 프록시가 인증 경계
- **설명**: PocketAide 백엔드가 `/api/sessions...` 계열 엔드포인트를 노출하고, 이를 **기존 OIDC 미들웨어 뒤**에 둔다. iOS 앱은 session-platform을 직접 호출하지 않으며, session-platform의 호스트·주소는 앱 바이너리·설정 어디에도 포함되지 않는다. 백엔드는 클러스터 내부 DNS(`http://control-plane.session-platform.svc.cluster.local`)로만 전달한다. 미인증·만료 토큰 요청은 401이며 어떤 경우에도 상위 플랫폼으로 전달되지 않는다. 프록시 응답은 원본 HTTP 상태 코드의 의미를 보존하되, 내부 토폴로지 정보(pod 이름, 내부 호스트명, 클러스터 경로)는 앱에 노출하지 않는다.
- **달성 가치**: V9
- **검증 방법**: 토큰 없이 `/api/sessions` 호출 → 401이고 컨트롤 플레인 접근 로그가 남지 않는지 확인. 유효 토큰 → 목록 반환. 앱 네트워크 트래픽 캡처에 session-platform 호스트가 등장하지 않는지 확인. 응답 JSON에 `pod` 등 내부 식별자가 포함되지 않는지 확인.

### AC2: 세션 소유권 매핑
- **설명**: session-platform에는 사용자 개념이 없으므로, PocketAide 백엔드가 `session_id ↔ user_id` 매핑을 자체 DB에 영속화한다. 목록·조회·쓰기·읽기·스냅샷·복원·삭제 **모든 경로**가 요청자 소유 세션으로 한정된다. 매핑에 없거나 타인 소유인 세션 id로의 요청은 존재 여부를 드러내지 않도록 **404**로 응답한다(403 아님). SPA나 다른 경로로 생성된 세션(`shell` 포함)은 앱 목록에 노출되지 않는다.
- **달성 가치**: V9
- **검증 방법**: 사용자 A가 만든 세션이 사용자 B의 목록에 없는지 확인. B가 A의 세션 id로 read/write/delete 시도 → 모두 404. SPA에서 직접 만든 세션이 앱 목록에 나타나지 않는지 확인. 세션 생성 성공 시 매핑 row가 정확히 1개 생성되는지 확인.

### AC3: claude-code 워크로드 고정
- **설명**: 앱을 통해 생성되는 모든 세션은 `workloadType=claude-code`로 고정된다. 클라이언트가 다른 값을 보내면 백엔드가 400으로 거부한다(무시하고 통과시키지 않는다 — 클라이언트 기대와 실제가 어긋나는 것을 막기 위함). 앱에는 `shell` 세션 생성 경로가 없다.
- **달성 가치**: V9
- **검증 방법**: 앱에서 생성한 세션의 `workloadType`이 항상 `claude-code`인지 확인. `workloadType=shell`을 명시한 요청 → 400 + pod 미생성 확인.

### AC4: 세션 생성 (이름 + 모델 선택)
- **설명**: 사용자가 세션 이름과 모델을 지정해 세션을 생성한다.
  - **이름**: 필수. 앞뒤 공백은 trim되며 공백만으로는 생성할 수 없다(400).
  - **모델**: `GET /api/v1/config`의 `claudeCode.models` 카탈로그를 선택지로 제공하고 기본 선택값은 `claudeCode.defaultModel`이다. 카탈로그가 비어 있으면 **자유 입력 필드로 대체**한다(카탈로그는 UI 힌트일 뿐 API allowlist가 아니다). 미지정 시 `platform-default`로 해석된다.
  - **불변성**: 모델과 워크로드는 생성 후 변경할 수 없다는 점을 생성 화면에서 명시한다.
  - **provisioning 지연**: 생성은 pod 프로비저닝을 수반해 수 초 이상 걸릴 수 있다. 진행 상태를 표시하고, 실패 시 사용자가 이해할 수 있는 원인(예: claude-code 이미지 미설정)을 노출한다.
- **달성 가치**: V9
- **검증 방법**: 카탈로그가 있는 환경/비어 있는 환경 각각에서 생성 UI가 선택지/자유 입력으로 올바르게 분기하는지 확인. 공백 이름 → 400. 생성 성공 → 상태 `active` + 지정한 모델이 세션 상세에 반영. 이미지 미설정 환경에서 실패 문구가 표시되는지 확인.

### AC5: 세션 목록과 상태 표시
- **설명**: 소유 세션을 목록으로 표시한다. 각 항목은 최소한 다음을 포함한다: 이름, 상태(`active` / `idle` / `snapshot`), 모델, 생성 시각, 마지막 접근 시각. 상태는 배지 등으로 시각적으로 구분되며, `snapshot` 항목은 체크포인트 생성 시각·크기를 함께 표시한다. 기본 정렬은 마지막 접근 시각 내림차순이다. **목록 조회는 세션 상태를 승격시키지 않는다** — 목록을 새로고침한다고 `idle` 세션이 `active`가 되거나 `snapshot`이 복원되지 않는다.
- **달성 가치**: V9
- **검증 방법**: 세 상태의 세션을 동시에 두고 각 배지가 올바른지 확인. 목록을 반복 새로고침해도 상태 전이·pod 생성이 발생하지 않는지 확인(플랫폼 측 pod 수 관찰). 당겨서 새로고침으로 상태 변화가 반영되는지 확인.

### AC6: 프롬프트 전송
- **설명**: 세션 화면에서 자연어 프롬프트를 전송한다. 백엔드는 이를 `POST /sessions/{id}/write`로 전달한다. **쓰기는 비동기 큐 등록이며 응답 완료를 뜻하지 않는다** — UI는 "전송됨"과 "응답 진행 중"과 "응답 완료"를 구분해 표시하고, 전송 성공을 작업 완료로 오인하게 하지 않는다. 프롬프트는 UTF-8 디코드 기준 1 MiB를 초과할 수 없으며, 앱은 전송 **전에** 초과를 안내하고 서버 413도 함께 처리한다. `idle` 세션에 쓰면 자동으로 `active`로 승격되고, `snapshot` 세션은 복원(AC9)이 선행되어야 한다.
- **달성 가치**: V9, V5
- **검증 방법**: 프롬프트 전송 → 출력 영역에 응답이 나타나는지 확인. 전송 직후 UI가 "완료"가 아닌 "진행 중"을 표시하는지 확인. 1 MiB 초과 입력 → 사전 안내 + 서버 413 처리 양쪽 확인. `idle` 세션에 전송 → `active` 승격 확인.

### AC7: 출력 이어보기 (커서 규약)
- **설명**: 출력은 **서버가 발급한 바이트 커서(`nextOffset`)** 를 기준으로 이어 읽는다. 클라이언트는 문자열 길이를 커서로 계산하지 않는다. 최초 진입은 `offset=0`으로 전체 이력을 받고, 앱 재진입·백그라운드 복귀 시 마지막 커서부터 이어받아 **중복·누락이 없어야 한다**. 요청 커서가 보존된 출력보다 앞서 있으면(reset 조건) 클라이언트는 부분 디코딩 상태를 폐기하고 `offset=0`으로 다시 읽은 뒤 그 응답의 `nextOffset`부터 이어간다. 표시되는 출력은 어시스턴트 텍스트 델타와 진단 stderr의 투영이며 `stream-json` 봉투는 노출되지 않는다. 누적 256 MiB 상한과 종료 마커는 UI에 그대로 반영한다.
- **달성 가치**: V9
- **검증 방법**: 긴 응답 스트리밍 중 앱을 백그라운드로 보냈다가 복귀 → 출력이 중복·누락 없이 이어지는지 확인. 커서를 인위적으로 현재 길이보다 크게 하여 reset 경로가 전체 재조회로 복구되는지 확인. 응답에 `stream-json` 원문 JSON이 노출되지 않는지 확인.

### AC8: 명시적 스냅샷 (게이트 오프 처리 포함)
- **설명**: 사용자가 세션을 명시적으로 스냅샷하여 pod를 반납할 수 있다. 성공하면 상태가 `snapshot`으로 바뀌고 체크포인트 정보(생성 시각·크기)가 표시된다. **`CLAUDE_CODE_ARCHIVE_ENABLED`가 꺼져 있으면 503이 반환되고 pod는 그대로 살아 있다.** 앱은 이를 "실패"가 아니라 "이 환경에서는 스냅샷이 비활성화되어 있으며 세션은 그대로 유지된다(데이터 손실 없음)"로 설명해야 한다.
- **달성 가치**: V9
- **검증 방법**: 게이트 온 환경 → 스냅샷 성공 + 상태 전이 + pod 회수 확인. 게이트 오프 환경 → 503 수신, 세션이 `active` 유지, 안내 문구가 손실을 시사하지 않는지 문구 검수.

### AC9: 복원 (재개)
- **설명**: `snapshot` 상태 세션은 명시적 "복원" 동작으로 새 pod에 복원한다(`POST /sessions/{id}/switch`). 복원은 수 초~수십 초 걸릴 수 있으므로 진행 상태를 표시하고, 완료 후 **이전 출력 이력과 커서가 그대로 이어진다**. 60분 무접근 시의 자동 idle→스냅샷 전이는 플랫폼이 수행하며, 앱은 그 결과 상태를 반영만 한다(앱이 자체 타이머로 스냅샷을 걸지 않는다). 전송 실패로 인한 자동 재시도가 `snapshot` 세션을 의도치 않게 복원시키지 않도록, 복원은 항상 사용자의 명시적 동작으로만 트리거된다.
- **달성 가치**: V9
- **검증 방법**: 스냅샷 세션 복원 → `active` 전이 + 이전 출력 유지 + 후속 프롬프트 처리 확인. 60분 방치 후 목록 상태가 자동으로 바뀌는지 확인. 네트워크 오류 후 자동 재시도 경로가 `snapshot` 세션을 복원시키지 않는지 확인.

### AC10: 세션 삭제
- **설명**: 세션 삭제는 되돌릴 수 없음을 명시한 확인 절차를 거친다. 성공 시 pod가 회수되고 플랫폼의 세션 레코드와 PocketAide의 소유 매핑 row가 함께 제거된다. **이미 업로드된 체크포인트/아카이브 오브젝트는 체크포인트 스토어의 보존 정책을 따르며 즉시 물리 삭제되지 않는다** — 이 점을 확인 문구에 반영한다.
- **달성 가치**: V9
- **검증 방법**: 삭제 → 목록에서 사라지고 동일 id 재조회가 404인지 확인. 소유 매핑 row가 제거되었는지 DB 확인. 확인 절차 없이 삭제가 실행되지 않는지 확인.

### AC11: 오류·한계 상황 가시화
- **설명**: 플랫폼이 응답하지 않거나 오류를 반환할 때, 앱은 사용자가 다음 행동을 결정할 수 있는 문구로 표시하고 재시도 동작을 제공한다. 최소한 다음을 서로 구분한다: 인증 실패(401 — 재로그인), 없음/권한 없음(404 — 목록 새로고침), 요청 과대(413 — 프롬프트 축소), 점유 충돌(409 — 잠시 후 재시도), 기능 비활성(503 — AC8 안내), 플랫폼 도달 불가/네트워크 오류(재시도). 내부 오류 원문을 그대로 노출하지 않는다.
- **달성 가치**: V9
- **검증 방법**: 각 상태 코드를 시뮬레이션 → 서로 다른 안내 문구와 적절한 복구 동작이 제시되는지 확인. 컨트롤 플레인을 중지한 상태에서 앱이 크래시 없이 도달 불가를 표시하는지 확인.

### AC12: 빈 상태와 로딩 상태
- **설명**: 소유 세션이 0개면 명확한 빈 상태 메시지와 세션 생성 유도를 표시한다. 목록·출력의 첫 로딩은 스켈레톤/스피너로 진행 상태를 표시한다. 출력이 아직 비어 있는 새 세션은 "아직 출력이 없습니다"와 프롬프트 입력 유도를 표시한다.
- **달성 가치**: V9
- **검증 방법**: 세션이 없는 계정으로 진입 → 빈 상태 확인. 네트워크 지연 상황에서 로딩 상태 확인. 갓 생성된 세션의 출력 영역 문구 확인.

## 결정 사항

- **접근 경로**: PocketAide 백엔드 프록시. iOS 앱은 기존 OIDC 토큰만 사용하며 session-platform을 직접 호출하지 않는다. 앱에 별도의 플랫폼 자격증명을 두지 않는다.
- **프록시 대상 주소**: 클러스터 내부 DNS `http://control-plane.session-platform.svc.cluster.local` (네임스페이스 `session-platform`, Service `control-plane`, port 80). 외부 도메인 경유하지 않는다.
- **1차 범위**: 전체 라이프사이클(생성·목록·프롬프트·출력·스냅샷·복원·삭제).
- **워크로드**: `claude-code` 전용. `shell`은 본 PRD 범위 밖.
- **소유권 모델**: PocketAide DB에 `session_id ↔ user_id` 매핑 테이블 신설. 플랫폼 측 스키마는 변경하지 않는다(플랫폼에 사용자 개념을 도입하지 않는다).
- **타인 세션 응답 코드**: 403이 아닌 404. 세션 존재 여부 자체를 노출하지 않기 위함.
- **모델 카탈로그 해석**: `GET /config`의 `models`는 UI 소프트 카탈로그이며 allowlist가 아니다. 비어 있으면 자유 입력을 유지한다.
- **스냅샷 정책**: 앱은 자동 스냅샷을 걸지 않는다. 플랫폼의 60분 idle 정책을 그대로 따르고, 명시적 스냅샷만 앱에서 트리거한다.
- **복원 트리거**: 사용자 명시 동작만. 자동 재시도·백그라운드 갱신은 `snapshot` 세션을 복원시키지 않는다.

## 운영 노트

- **크로스 네임스페이스 통신**: `pocket-aide` 네임스페이스의 백엔드 pod가 `session-platform` 네임스페이스의 Service에 접근한다. 현재 NetworkPolicy는 확인되지 않았으나, 도입 시 이 경로를 명시적으로 허용해야 한다.
- **스냅샷 게이트**: `CLAUDE_CODE_ARCHIVE_ENABLED`는 프로덕션 기본 off다. 게이트가 꺼진 상태로 배포하면 AC8의 503 경로가 **정상 동작**이며, 사용자에게는 비활성 안내로 보여야 한다.
- **세션 = pod**: 세션 1개가 실제 pod 1개다. 폰에서 생성이 쉬워지는 만큼 방치 세션이 늘어날 수 있다. 60분 idle 스냅샷이 1차 방어선이지만, 스냅샷 게이트가 off면 pod가 계속 살아 있다는 점에 유의.
- **출력 상한**: 누적 256 MiB, 호출당 16 MiB 상한이 플랫폼 측에 존재한다. 모바일에서 전체 이력(`offset=0`) 재조회는 비용이 크므로 커서 보존이 실질적으로 중요하다.

## 열린 질문

- **V9 해석 범위 (결정 필요)**: 본 PRD의 12개 AC는 모두 V9(또는 V9+V5)에 매핑되어 있으나, V9의 현재 설명문은 PR·CI 상태 확인에 한정되어 있다. (a) V9 설명을 "상태 파악"에서 "개발 작업의 원격 수행"까지 넓히거나, (b) 능동적 실행을 별도 가치로 분리하는 두 선택지가 있다. 결정 전까지 위 "가치 해석 노트"가 임시 근거 역할을 한다.
- **출력 전송 방식 (결정 필요)**: 플랫폼은 SSE(`GET /sessions/{id}/stream`, `Last-Event-ID` 재개)와 커서 기반 `POST /read` 두 경로를 제공한다. 프록시가 SSE를 중계할지, 1차는 포그라운드 폴링으로 갈지 결정 필요.
  - *추천*: 1차는 포그라운드에서 `POST /read` 폴링(약 2초 간격). 이유 — iOS 백그라운드 서스펜션으로 롱리브 커넥션이 자주 끊기고, 프록시가 사용자·세션마다 커넥션을 유지하는 비용이 크며, AC7의 커서 규약만 지키면 폴링→SSE 전환 시 클라이언트 로직이 그대로 재사용된다. SSE 프록시는 후속.
- **응답 완료 푸시 (1차 제외, 후속 1순위)**: 에이전트 응답이 끝났을 때 APNs 푸시를 보내면 V9 관점에서 가치가 크다. 그러나 플랫폼에 완료 콜백·이벤트가 없어 백엔드가 출력 커서를 폴링해 완료를 추론해야 하므로 별도 설계가 필요하다. PRD-10의 APNs 인프라를 재사용할 수 있다.
- **session-platform 외부 노출 정책 (보안 검토 필요)**: 현재 컨트롤 플레인은 `session-platform.${PRIVATE_DOMAIN}`에 `allow-internal-only`로 노출되어 있고 API 자체에는 인증이 없다. PocketAide는 `pocket-aide.${PUBLIC_DOMAIN}` 공용 도메인이므로, 프록시 도입은 **인증 없는 내부 전용 API를 공용망에 잇는 다리**를 만드는 일이다. 프록시를 유일한 외부 진입점으로 좁힐지, 기존 내부 경로를 유지할지, 플랫폼 자체에 인증을 도입할지 결정 필요.
- **사용자당 동시 세션 상한**: 세션 1개 = pod 1개. 폰에서 생성이 쉬워지므로 상한을 둘지 결정 필요.
- **세션 이름 입력 부담**: 폰 입력 특성상 이름 필수가 마찰이 될 수 있다. 자동 이름 제안(첫 프롬프트 요약 등)을 둘지 검토.
- **음성 프롬프트 연계 (1차 제외)**: V1(핸즈프리 즉시 캡처)·V2(한·영 혼용 인식)와 결합해 숏컷에서 바로 프롬프트를 전송하는 흐름. 본 PRD 범위 밖이나 폰에서의 세션 운용과 강하게 보완된다.
- **오프라인·전송 실패 시 프롬프트 보존**: 지하철 등 불안정 네트워크에서 작성한 프롬프트를 로컬 큐에 보관했다가 재전송할지. 재전송이 AC9의 "명시적 복원만" 원칙과 충돌하지 않도록 설계 필요.

## 후속 작업

1. 응답 완료 APNs 푸시 (PRD-10 인프라 재사용).
2. SSE 프록시로 출력 전송 방식 전환.
3. 음성 프롬프트 전송 (V1·V2·V5 연계).
4. 사용자당 세션 상한·쿼터.
5. `shell` 워크로드 지원 여부 재검토.
