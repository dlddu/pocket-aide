# PRD: GitHub PR·CI 모니터링 화면

## 달성 가치
- **V9**: 개발 워크플로우 인지 부하 감소 — 열려 있는 PR과 그 CI 상태를 별도 도구 전환 없이 한 화면에서 파악. CI 완료는 푸시로 받아 의식적 폴링 부담을 제거.

## 개요

PocketAide 앱 내에 사용자의 GitHub 활동 상태를 모니터링하는 화면을 추가한다. 이 화면은 다음 두 기능을 제공한다:

1. **PR·CI 통합 뷰**: 사용자가 작성자이거나 리뷰어로 지정된 **열려 있는(open) PR** 목록을 보여주고, 각 PR의 최신 CI 실행 상태를 함께 표시한다.
2. **CI 완료 푸시 알림**: 사용자가 관심을 가지는 PR의 CI 실행이 완료되면(성공/실패 무관) 시스템 푸시 알림을 보낸다.

목적은 개발 작업 중 "PR 어떻게 됐지?", "CI 통과했나?" 확인을 위해 컨텍스트를 이탈하는 빈도를 줄이는 것이다.

## 사용자 시나리오 (대표)

1. 사용자가 PR을 올리고 회사 슬랙으로 돌아간다 → 몇 분 뒤 폰에 푸시: "CI 통과 — feature/login (#123)" → 다음 작업으로 자연스럽게 이어감.
2. 점심시간 폰을 켜고 PocketAide 진입 → 모니터링 탭에서 자신의 열린 PR 5개와 각 CI 상태(✅ 3 / ❌ 1 / 🟡 1)를 한 눈에 본다.
3. 실패 알림을 받음 → 알림 탭 → 앱이 해당 PR 상세 (외부 GitHub 링크)로 진입.
4. 점심 후 자리에 돌아와 PR 모니터 탭을 연다 → 이력 목록 상단에 `Repo A · PR #123 — 5건 / 미확인 2` 그룹 카드가 미확인 강조로 노출 → 그룹을 펼쳐 미확인 두 항목만 "확인" 버튼으로 빠르게 처리. 이미 확인한 어제 항목들은 dim 처리되어 시야를 방해하지 않는다.

## Acceptance Criteria

### AC1: GitHub 계정 연결
- **설명**: 사용자가 GitHub 계정을 본 앱에 연결할 수 있다. OAuth 또는 Personal Access Token 기반으로 한다. 연결 해제 / 토큰 갱신도 가능하다.
- **달성 가치**: V9
- **검증 방법**: 설정에서 GitHub 연결 → 성공 시 사용자 핸들 표시 → 연결 해제 시 데이터 접근 차단 확인.

### AC2: 열린 PR 목록 표시
- **설명**: 모니터링 화면에서 사용자가 **작성자** 또는 **리뷰어**로 지정된 모든 열린(open) PR을 목록으로 표시한다. 각 항목은 최소한 다음을 포함한다: 레포 이름, PR 번호, PR 제목, 작성자, 마지막 갱신 시각, 사용자의 역할(작성자/리뷰어).
- **달성 가치**: V9
- **검증 방법**: GitHub에서 새 PR 생성 → 모니터링 화면에 노출되는지 확인. PR 닫힘/머지 시 목록에서 사라지는지 확인.

### AC3: PR별 최신 CI 상태 표시
- **설명**: 각 PR 항목에 그 PR HEAD 커밋의 최신 CI 실행 상태가 함께 표시된다. 상태는 최소한 네 가지로 구분된다: 진행 중(in_progress/queued), 성공(success), 실패(failure/error), 상태 없음(체크 미실행). 여러 체크가 있을 경우 종합 상태를 보여준다(전부 성공 = 성공, 하나라도 실패 = 실패, 나머지 = 진행 중).
- **달성 가치**: V9
- **검증 방법**: 빌드 실행 중인 PR과 완료된 PR을 동시에 두고 각 상태가 올바르게 매핑되는지 확인.

### AC4: 정렬과 필터
- **설명**: 목록은 기본적으로 "마지막 갱신 시각 내림차순"으로 정렬된다. 사용자가 다음 필터를 토글할 수 있다: 내 PR만 / 리뷰 요청만 / CI 실패만. 필터 상태는 화면 재진입 시 유지된다.
- **달성 가치**: V9
- **검증 방법**: 각 필터 적용 → 결과 목록이 예상대로 좁혀지는지 확인. 앱 재진입 시 마지막 필터 유지 확인.

### AC5: 수동 새로고침
- **설명**: 사용자가 당겨서 새로고침(pull-to-refresh) 으로 즉시 목록과 상태를 갱신할 수 있다. 마지막 갱신 시각이 화면에 표시된다.
- **달성 가치**: V9
- **검증 방법**: PR 상태 변경 직후 새로고침 → 변경이 반영되는지 확인.

### AC6: 워크플로우 완료 푸시 (서버 웹훅 → APNs)
- **설명**: 앱이 백그라운드에 있거나 종료된 상태에서도, **사용자가 명시적으로 제외하지 않은 레포**의 GitHub Actions 워크플로우 실행이 **종료(성공/실패 모두)** 되면 시스템 푸시 알림이 도달한다. 알림은 최소한 결과 상태와 식별 정보(레포 이름; PR 연결이 있으면 PR 번호·제목 축약, 없으면 워크플로우/브랜치)를 포함한다. 푸시는 서버가 GitHub `workflow_run` 웹훅을 (AWS EventBridge → SQS 경유로) 수신해 APNs로 발송한다(클라이언트 폴링 아님). 매칭 모델은 **blacklist** — 사용자별 제외 레포 목록(`user_excluded_repos`)에 포함되지 않은 모든 레포의 이벤트가 그 사용자에게 발송된다.
- **달성 가치**: V9
- **검증 방법**: 앱 백그라운드 진입 → 외부에서 워크플로우 실행 → 완료 시점에 푸시 도달 확인. (i) 성공/실패 양쪽 (ii) PR 연결 있는 케이스 / 없는 케이스(예: main 직접 푸시) 양쪽 (iii) 제외한 레포는 푸시 미도달 확인.

### AC7: 알림 탭 시 해당 PR로 진입
- **설명**: 푸시 알림을 탭하면 앱이 열리고, 가능한 경우 해당 PR을 식별할 수 있는 화면(모니터링 목록의 해당 항목 강조 또는 PR 상세/외부 링크) 로 이동한다. 푸시 탭은 진입·라우팅만 담당하며, AC12의 "확인 처리"는 트리거하지 않는다(아래 AC12 참조).
- **달성 가치**: V9
- **검증 방법**: 푸시 도달 → 탭 → 해당 PR이 가시화되는 화면에 도달 확인. 동시에 해당 이력 항목의 확인 상태가 변경되지 않았는지 확인.

### AC8: 알림 설정 제어
- **설명**: 사용자가 푸시 알림을 다음 단위로 제어할 수 있다: 전체 켜기/끄기, 성공만/실패만/둘 다, 특정 레포 제외. 시스템 알림 권한이 거부되어 있으면 화면에 안내한다.
- **달성 가치**: V9
- **검증 방법**: 각 설정 변경 → 후속 CI 완료 이벤트의 알림 도달/미도달이 설정과 일치하는지 확인.

### AC9: 인증·권한 오류 가시화
- **설명**: 토큰 만료, 권한 불충분(예: private 레포 접근 불가), 레이트 리밋 도달 등 사용자가 인지해야 할 오류가 발생하면 화면 상단에 명확한 배너로 표시하고, 해결 동작(재인증, 토큰 갱신 등)을 제공한다.
- **달성 가치**: V9
- **검증 방법**: 만료된 토큰으로 진입 → 배너 노출 확인. 재인증 후 정상화 확인.

### AC10: 빈 상태와 로딩 상태
- **설명**: 열린 PR이 0개인 경우 명확한 빈 상태 메시지를 표시한다("열려 있는 PR이 없습니다"). 첫 로딩 시 스켈레톤/스피너로 진행 상태를 표시한다.
- **달성 가치**: V9
- **검증 방법**: 열린 PR이 없는 계정으로 진입 → 빈 상태 확인. 네트워크 지연 시 로딩 상태 확인.

### AC11: CI 완료 알림 이력 보존
- **설명**: 서버가 수신한 모든 CI 완료 이벤트(workflow_run completed)는 푸시 발송과 무관하게 서버 측에 이력 항목으로 영속화된다. 각 항목은 최소한 다음을 포함한다: 식별자(id), PR 링크(없을 수 있음), 커밋 링크, workflow run 링크, 확인 여부, 확인 시각. 사용자는 모니터링 화면에서 이 이력을 조회할 수 있으며, 조회 화면은 **미확인 항목과 확인 항목을 시각적으로 명확히 구분**한다(예: 미확인은 강조 스타일·인디케이터, 확인은 dim·취소선·점선 보더 등 약한 시각 강도). 기본 정렬은 **미확인 우선, 그 다음 시각 역순**이며, 화면 상단에는 현재 미확인 항목 **총 개수 배지**가 표시된다. 이력 항목은 푸시 발송보다 **먼저** 기록되어야 하며, 저장에 실패하면 푸시 발송도 진행하지 않고 이벤트는 재시도 큐에 남는다.
- **달성 가치**: V9
- **검증 방법**: workflow_run 이벤트 수신 → 서버 DB에 이력 항목 생성 확인 → 클라이언트 모니터링 화면에서 조회 가능 확인. 미확인 항목이 시각적으로 강조되고 확인 항목이 dim 처리되어 한눈에 구분되는지 검수. 미확인 항목이 목록 상단에 우선 노출되는지 확인. 화면 상단의 미확인 개수 배지가 항목 확인 처리에 따라 실시간으로 감소하는지 확인. DB 저장 실패를 시뮬레이션 → 푸시가 발송되지 않고 메시지가 재처리되는지 확인.

### AC12: 알림 이력의 명시적 확인 처리
- **설명**: 사용자는 모니터링 화면의 이력 항목별 "확인" 버튼으로 해당 항목을 처리할 수 있다. 확인된 항목은 확인 시각이 기록되고 시각적으로 미확인 항목과 구분된다(AC11). 그룹(AC13) 내부에서도 확인 동작은 **개별 항목 단위**로만 트리거되며, 그룹 헤더의 미확인 카운트는 그룹 내 미확인 row 수의 집계 결과를 실시간 반영한다. 푸시 알림 탭(AC7) 또는 이력 항목 내 외부 링크 탭은 확인 처리를 **트리거하지 않는다** — 명시적 버튼 클릭만이 확인 트리거이다.
- **달성 가치**: V9
- **검증 방법**: 미확인 이력 항목에 "확인" 버튼 클릭 → 시각적 구분 적용 + `acknowledged_at` 기록 확인. 같은 그룹의 다른 항목은 미확인 상태로 유지되는지 + 그룹 헤더의 미확인 수가 1만큼 감소했는지 확인. 푸시 탭이나 외부 링크 탭을 수행해도 항목이 미확인 상태로 유지되는지 확인.

### AC13: 이력 목록의 PR/커밋 단위 그룹핑
- **설명**: 동일 PR 또는 동일 커밋에 대해 여러 workflow_run completed 이벤트가 도달하면(예: 한 PR에서 다수의 워크플로우가 실행되거나, 한 워크플로우가 재실행되거나, 같은 브랜치에 연속 push가 일어나는 경우), 이력 목록은 이를 **하나의 그룹 카드**로 묶어 표시한다. 그룹 키는 다음과 같이 결정된다:
    - PR 정보가 있는 경우(`workflow_run.pull_requests`가 비어 있지 않음): `(repo_owner, repo_name, pr_number)`
    - PR 정보가 없는 경우(예: main 직접 푸시): `(repo_owner, repo_name, head_sha)`

  각 그룹 카드 헤더는 그룹 키 정보(레포 이름 + PR 번호·제목 축약 또는 커밋 SHA 축약), 그룹 내 항목 수, **미확인 항목 수**, 그룹 종합 상태 요약(예: `✅ 3 / ❌ 1 / 🟡 1`), 가장 최근 이벤트 시각을 표시한다. 그룹을 펼치면 내부의 개별 워크플로우 이벤트 항목들이 시각 역순으로 나열된다. 데이터 모델은 워크플로우 실행 단위 row를 그대로 유지하며, 그룹핑은 **표시·조회 단계에서만** 수행된다(서버 응답이 그룹 키와 함께 row를 내려주거나, 클라이언트가 키로 묶는다). 확인 동작(AC12)은 그룹 내 개별 항목 단위로만 트리거되며, 그룹 단위 일괄 확인은 본 AC의 범위에서 제외한다(후속 작업 참조).
- **달성 가치**: V9
- **검증 방법**: 동일 PR에 두 개 이상의 workflow_run completed 이벤트가 도달하도록 시뮬레이션(또는 실제 PR에 다수 워크플로우 실행) → 이력 목록에서 단일 그룹 카드로 묶여 노출되는지 확인. 그룹 헤더에 항목 수·미확인 수·종합 상태가 올바르게 집계되는지 확인. PR 정보 없는 케이스(main 직접 푸시 등)는 `head_sha` 단위로 묶이는지 확인. 그룹 내 항목을 개별 확인했을 때 그룹 헤더의 미확인 수가 올바르게 감소하는지 확인. 단일 이벤트만 있는 PR/커밋도 1개짜리 그룹 카드로 일관되게 표시되는지 확인.

## 결정 사항

이번 구현(AC6·AC7·AC11·AC12) 진행 중 확정된 사항. 이전 "열린 질문"에서 해소된 항목.

- **푸시 모델**: 서버 측 GitHub 웹훅 수신 → APNs 푸시. iOS BGAppRefreshTask 기반 폴링은 채택하지 않음. 백엔드는 EventBridge → SQS → Go 컨슈머 → APNs 경로로 처리.
- **서버 컴포넌트 활용 범위**: 기존 Go 백엔드(`backend/`)를 그대로 사용. 별도 서비스는 두지 않음. SQLite 단일 DB에 사용자 매칭·이력·디바이스 토큰을 영속화.
- **CI 시스템 범위 (1차)**: GitHub Actions의 `workflow_run` 이벤트만 다룬다. Checks API(외부 CI 종합) 통합은 후속.
- **매칭 모델**: blacklist 방식. `user_excluded_repos` 테이블이 비어 있으면 해당 사용자에게 모든 워크플로우 완료 이벤트가 도달. PRD-10의 "관심 PR" 개념(작성자/리뷰어 한정)은 AC6에서는 사용하지 않으며, AC2 구현 시 재정의한다.
- **PR 정보 없는 케이스**: `workflow_run.pull_requests`가 비어 있어도(예: main 직접 푸시) 푸시·이력 모두 발송한다. 표시 텍스트는 `repo — conclusion · workflow_name`으로 fallback.
- **알림 이력 보존 정책**: 영구 보존. N일 만료·확인 시 삭제는 채택하지 않음.
- **이력 행 모델**: 매칭된 사용자 수만큼 row 복제. 각 row는 PK + `user_id`로 식별되며, ack(`acknowledged_at`)는 본인 row에만 적용된다.
- **모니터링 화면 구성**: 알림 이력은 **RootView의 7번째 일상 탭("PR 모니터")** 내부 화면에 둔다. AC2의 "열린 PR 목록"은 별도 후속 화면.
- **푸시 페이로드**: APNs custom data로 `event_id`(서버에서 부여한 이력 ID) 한 필드만 포함. 푸시 탭 → deep-link `pocketaide://pr-monitor?eventId=<id>` → PR 모니터 탭의 해당 항목 강조 (확인은 트리거하지 않음, AC7·AC12 분리).
- **이력 저장 실패 시 동작**: SQS `DeleteMessage` 건너뜀 + visibility timeout 30초로 자연 재시도. 운영자는 SQS 큐 속성에서 `VisibilityTimeout=30`을 설정해야 한다(코드 외 작업).
- **이력 표시 모델 — 확인/미확인 구분 (AC11)**: 미확인 항목은 강조 스타일, 확인 항목은 dim/취소선 등 약한 시각 강도로 명확히 구분. 기본 정렬은 미확인 우선, 그 다음 시각 역순. 화면 상단에 미확인 총 개수 배지.
- **이력 표시 모델 — PR/커밋 단위 그룹핑 (AC13)**: 이력 목록은 PR(있으면) 또는 `head_sha`(없으면)를 키로 표시 단계에서 그룹핑한다. 데이터 모델은 워크플로우 실행 단위 row를 그대로 유지하며, 그룹은 표시 차원의 묶음. 그룹은 카드 형태로 헤더(항목 수·미확인 수·종합 상태·최근 시각)와 펼침 영역(개별 이벤트 row)을 가진다.
- **그룹 확인 처리 범위 (1차)**: 확인은 항목 단위로만 트리거. 그룹 단위 일괄 확인은 후속(아래 후속 작업 참조).
- **푸시 알림의 시스템 그룹핑 (1차 제외)**: APNs `thread-id` 등을 이용한 OS 알림 센터 측 그룹핑은 본 PRD 범위에서 제외(후속 검토). AC6의 푸시는 각 workflow_run completed 이벤트당 1회 발송 모델을 유지.

## 운영 노트

- **SQS VisibilityTimeout**: 30초로 설정해야 단계 9의 재시도 동작이 작동한다. 기본값(30초)이면 변경 불필요. AWS 콘솔/IaC 측에서 확인 필요.
- **APNs 발송 실패**: best-effort. 이력은 저장되었으나 푸시만 누락된 사용자는 PR 모니터 탭 진입 시 미확인 카드로 확인 가능. APNs 실패 로그는 운영 모니터링 대상.

## 남은 열린 질문

- **GitHub Enterprise 지원 여부**: 사용자의 회사 GitHub가 Enterprise(자체 호스팅)인 경우 별도 호스트 설정이 필요한지 결정 필요. (보류)
- **CODEOWNERS·팀 리뷰 매칭** (AC2 후속): 작성자/리뷰어 외 CODEOWNERS, 팀 리뷰 요청까지 "관심 PR"에 포함할지. (보류)

## 후속 작업 (이번 범위 밖)

이번 PR에서는 AC6·AC7·AC11·AC12만 다룬다. 아래 AC는 별도 PR에서 진행.

- **AC1**: GitHub 계정 연결 (OAuth/PAT 흐름, 토큰 저장)
- **AC2**: 열린 PR 목록 표시
- **AC3**: PR별 CI 상태 표시
- **AC4**: 정렬·필터 (내 PR만 / 리뷰 요청만 / CI 실패만)
- **AC5**: 수동 새로고침 (pull-to-refresh, 마지막 갱신 시각)
- **AC8**: 알림 설정 제어 (전체 on/off, 성공만/실패만, 레포 제외 UI — 이번 범위의 "제외 레포 관리"는 PR 모니터 화면 내부 sheet로만 노출)
- **AC9**: 인증·권한 오류 가시화 배너
- **AC10**: 빈 상태·로딩 상태 정형화
- **그룹 단위 일괄 확인 액션**: 그룹 헤더에서 그룹 내 모든 미확인 항목을 한 번에 확인 처리하는 UX. 1차 범위 제외(AC13 결정 사항 참조). 사용자 검증 후 별도 AC로 추가.
- **푸시 알림의 OS 그룹핑**: APNs `thread-id`를 PR/커밋 단위로 부여하여 iOS 알림 센터에서 같은 PR/커밋의 알림이 자동 묶이도록. 본 PRD 범위 제외.
