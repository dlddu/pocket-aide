# PRD: GitHub PR·CI 모니터링 화면

## 달성 가치
- **V9**: 개발 워크플로우 인지 부하 감소 — 열려 있는 PR과 그 CI 상태를 별도 도구 전환 없이 한 화면에서 파악. CI 완료는 푸시로 받아 의식적 폴링 부담을 제거.

## 개요

PocketAide 앱 내에 사용자의 GitHub 활동 상태를 모니터링하는 화면을 추가한다. 이 화면은 다음 두 기능을 제공한다:

1. **PR·CI 통합 뷰**: 사용자가 작성자이거나 리뷰어로 지정된 **열려 있는(open) PR** 목록을 보여주고, 각 PR의 최신 CI 실행 상태를 함께 표시한다.
2. **CI 완료 푸시 알림**: 사용자가 관심을 가지는 PR의 CI 실행이 완료되면(성공/실패 무관) 시스템 푸시 알림을 보낸다.

목적은 개발 작업 중 "PR 어떻게 됐지?", "CI 통과했나?" 확인을 위해 컨텍스트를 이탈하는 빈도를 줄이는 것이다.

## 사용자 시나리오 (대표)

1. 사용자가 PR을 올리고 회사 슬랙으로 돌아간다 → 몇 분 뒤 폰에 푸시: "CI 통과 — feature/login (#123)" → 다음 작업으로 자연스럽게 이어감.
2. 점심시간 폰을 켜고 PocketAide 진입 → 모니터링 탭에서 자신의 열린 PR 5개와 각 CI 상태(✅ 3 / ❌ 1 / 🟡 1)를 한 눈에 본다.
3. 실패 알림을 받음 → 알림 탭 → 앱이 해당 PR 상세 (외부 GitHub 링크)로 진입.

## Acceptance Criteria

### AC1: GitHub 계정 연결
- **설명**: 사용자가 GitHub 계정을 본 앱에 연결할 수 있다. OAuth 또는 Personal Access Token 기반으로 한다. 연결 해제 / 토큰 갱신도 가능하다.
- **달성 가치**: V9
- **검증 방법**: 설정에서 GitHub 연결 → 성공 시 사용자 핸들 표시 → 연결 해제 시 데이터 접근 차단 확인.

### AC2: 열린 PR 목록 표시
- **설명**: 모니터링 화면에서 사용자가 **작성자** 또는 **리뷰어**로 지정된 모든 열린(open) PR을 목록으로 표시한다. 각 항목은 최소한 다음을 포함한다: 레포 이름, PR 번호, PR 제목, 작성자, 마지막 갱신 시각, 사용자의 역할(작성자/리뷰어).
- **달성 가치**: V9
- **검증 방법**: GitHub에서 새 PR 생성 → 모니터링 화면에 노출되는지 확인. PR 닫힘/머지 시 목록에서 사라지는지 확인.

### AC3: PR별 최신 CI 상태 표시
- **설명**: 각 PR 항목에 그 PR HEAD 커밋의 최신 CI 실행 상태가 함께 표시된다. 상태는 최소한 네 가지로 구분된다: 진행 중(in_progress/queued), 성공(success), 실패(failure/error), 상태 없음(체크 미실행). 여러 체크가 있을 경우 종합 상태를 보여준다(전부 성공 = 성공, 하나라도 실패 = 실패, 나머지 = 진행 중).
- **달성 가치**: V9
- **검증 방법**: 빌드 실행 중인 PR과 완료된 PR을 동시에 두고 각 상태가 올바르게 매핑되는지 확인.

### AC4: 정렬과 필터
- **설명**: 목록은 기본적으로 "마지막 갱신 시각 내림차순"으로 정렬된다. 사용자가 다음 필터를 토글할 수 있다: 내 PR만 / 리뷰 요청만 / CI 실패만. 필터 상태는 화면 재진입 시 유지된다.
- **달성 가치**: V9
- **검증 방법**: 각 필터 적용 → 결과 목록이 예상대로 좁혀지는지 확인. 앱 재진입 시 마지막 필터 유지 확인.

### AC5: 수동 새로고침
- **설명**: 사용자가 당겨서 새로고침(pull-to-refresh) 으로 즉시 목록과 상태를 갱신할 수 있다. 마지막 갱신 시각이 화면에 표시된다.
- **달성 가치**: V9
- **검증 방법**: PR 상태 변경 직후 새로고침 → 변경이 반영되는지 확인.

### AC6: 백그라운드 폴링 및 CI 완료 푸시
- **설명**: 앱이 백그라운드에 있거나 종료된 상태에서도, 사용자의 관심 PR(작성자이거나 리뷰어로 지정된 열린 PR)의 CI 실행이 **진행 중 → 종료(성공/실패)** 로 전환되면 시스템 푸시 알림을 보낸다. 알림은 최소한 PR 식별 정보(레포 + PR 번호 + 제목 축약)와 결과 상태를 포함한다.
- **달성 가치**: V9
- **검증 방법**: 앱 백그라운드 진입 → 외부에서 PR의 CI 실행 → 완료 시점에 푸시 도달 확인. 성공/실패 양쪽 검증.

### AC7: 알림 탭 시 해당 PR로 진입
- **설명**: 푸시 알림을 탭하면 앱이 열리고, 가능한 경우 해당 PR을 식별할 수 있는 화면(모니터링 목록의 해당 항목 강조 또는 PR 상세/외부 링크) 로 이동한다. 푸시 탭은 진입·라우팅만 담당하며, AC12의 "확인 처리"는 트리거하지 않는다(아래 AC12 참조).
- **달성 가치**: V9
- **검증 방법**: 푸시 도달 → 탭 → 해당 PR이 가시화되는 화면에 도달 확인. 동시에 해당 이력 항목의 확인 상태가 변경되지 않았는지 확인.

### AC8: 알림 설정 제어
- **설명**: 사용자가 푸시 알림을 다음 단위로 제어할 수 있다: 전체 켜기/끄기, 성공만/실패만/둘 다, 특정 레포 제외. 시스템 알림 권한이 거부되어 있으면 화면에 안내한다.
- **달성 가치**: V9
- **검증 방법**: 각 설정 변경 → 후속 CI 완료 이벤트의 알림 도달/미도달이 설정과 일치하는지 확인.

### AC9: 인증·권한 오류 가시화
- **설명**: 토큰 만료, 권한 불충분(예: private 레포 접근 불가), 레이트 리밋 도달 등 사용자가 인지해야 할 오류가 발생하면 화면 상단에 명확한 배너로 표시하고, 해결 동작(재인증, 토큰 갱신 등)을 제공한다.
- **달성 가치**: V9
- **검증 방법**: 만료된 토큰으로 진입 → 배너 노출 확인. 재인증 후 정상화 확인.

### AC10: 빈 상태와 로딩 상태
- **설명**: 열린 PR이 0개인 경우 명확한 빈 상태 메시지를 표시한다("열려 있는 PR이 없습니다"). 첫 로딩 시 스켈레톤/스피너로 진행 상태를 표시한다.
- **달성 가치**: V9
- **검증 방법**: 열린 PR이 없는 계정으로 진입 → 빈 상태 확인. 네트워크 지연 시 로딩 상태 확인.

### AC11: CI 완료 알림 이력 보존
- **설명**: 서버가 수신한 모든 CI 완료 이벤트(workflow_run completed)는 푸시 발송과 무관하게 서버 측에 이력 항목으로 영속화된다. 각 항목은 최소한 다음을 포함한다: 식별자(id), PR 링크(없을 수 있음), 커밋 링크, workflow run 링크, 확인 여부, 확인 시각. 사용자는 모니터링 화면에서 이 이력을 조회할 수 있다. 이력 항목은 푸시 발송보다 **먼저** 기록되어야 하며, 저장에 실패하면 푸시 발송도 진행하지 않고 이벤트는 재시도 큐에 남는다.
- **달성 가치**: V9
- **검증 방법**: workflow_run 이벤트 수신 → 서버 DB에 이력 항목 생성 확인 → 클라이언트 모니터링 화면에서 조회 가능 확인. DB 저장 실패를 시뮬레이션 → 푸시가 발송되지 않고 메시지가 재처리되는지 확인.

### AC12: 알림 이력의 명시적 확인 처리
- **설명**: 사용자는 모니터링 화면의 이력 항목별 "확인" 버튼으로 해당 항목을 처리할 수 있다. 확인된 항목은 확인 시각이 기록되고 시각적으로 미확인 항목과 구분된다. 푸시 알림 탭(AC7) 또는 이력 항목 내 외부 링크 탭은 확인 처리를 **트리거하지 않는다** — 명시적 버튼 클릭만이 확인 트리거이다.
- **달성 가치**: V9
- **검증 방법**: 미확인 이력 항목에 "확인" 버튼 클릭 → 시각적 구분 적용 + `acknowledged_at` 기록 확인. 푸시 탭이나 외부 링크 탭을 수행해도 항목이 미확인 상태로 유지되는지 확인.

## 열린 질문

- **백그라운드 폴링 주기**: iOS의 백그라운드 실행 제약(BGAppRefreshTask 등) 안에서 어느 주기로 CI 상태를 폴링할지. 너무 잦으면 배터리·레이트 리밋 문제, 너무 드물면 알림 지연. → 서버 측에 GitHub 웹훅을 받아두고 본 앱에 푸시하는 모델로 갈지, 클라이언트 폴링으로 갈지 결정 필요.
- **서버 컴포넌트 필요 여부**: AC6의 안정적 푸시를 위해 백엔드(이미 존재하는 Go 백엔드 활용)에서 GitHub 웹훅 수신 → APNs로 푸시하는 구조가 필요한지 결정 필요. 클라이언트만으로 처리할 경우 앱이 닫혀 있을 때의 신뢰성이 떨어진다.
- **"관심 PR"의 범위**: AC6 기준이 현재는 "작성자 또는 리뷰어로 지정된 열린 PR"이다. CODEOWNERS 매칭, 팀 리뷰 요청 등 더 넓은 범위를 포함할지 결정 필요.
- **GitHub Enterprise 지원 여부**: 사용자의 회사 GitHub가 Enterprise(자체 호스팅)인 경우 별도 호스트 설정이 필요한지 결정 필요.
- **CI 시스템 범위**: GitHub Actions만 다룰지, 외부 CI(Buildkite, CircleCI 등)가 GitHub Checks API로 등록한 상태도 모두 다룰지. AC3은 Checks API 기준으로 작성되어 외부 CI도 포함하는 방향이지만 확정 필요.
- **연결 방식**: AC1에서 OAuth와 PAT 중 어느 쪽을 1차로 지원할지. OAuth가 사용자 경험은 낫지만 OAuth App 등록·승인 필요. PAT가 구현 단순.
- **알림 이력 보존 정책**(AC11 관련): 영구 보존 / N일 후 자동 삭제 / 확인 처리 시 삭제 등의 정책 결정 필요. 현재 단계에서는 일단 영구 보존을 전제로 한다.
- **모니터링 화면 구성**(AC2/AC11 관련): "열린 PR 목록"(AC2)과 "CI 완료 알림 이력"(AC11)을 동일 화면의 두 섹션으로 둘지, 별도 탭/스크린으로 둘지 결정 필요. 두 정보는 시간 축이 다르다(전자는 현재 상태, 후자는 과거 이벤트).
