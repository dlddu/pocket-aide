## 작성 기준
- 시나리오는 **사용자가 관찰할 수 있는 결과** 단위로 쓴다. 코드 레벨 테스트는 각 시나리오의
  「관련 코드 테스트」에 참고로만 적으며, 시나리오의 검증을 대신하지 않는다.
- 「구현 상태」는 작성 시점(2026-10-01, `main` `ed25851`) 코드 기준이다. 위젯 구현은 #29(Large 5영역 골격 +
  다짐 회전)까지이며, 다짐을 뺀 네 영역(날씨·다음 일정·메일·알림)은 라벨과 「곧 추가」 문구만 있는 자리다.
- 「부분 구현」은 AC의 일부 관측 대상은 있으나 기대 결과 전부를 충족하지 못하는 상태다. 어긋나는 지점을 그 자리에 적는다.
- 위젯은 **Large 크기만** 제공된다. 크기별 표현 차이(AC1 「축약/확장」)는 PRD상 선택이라 시나리오에 넣지 않았다.
- 다짐 탭 쪽에서 본 위젯 연계(PRD-5 AC4)는 `test-affirmations.md` 시나리오 7이 검증한다. 이 문서의 시나리오 5는
  위젯 쪽 요구(PRD-8 AC5 — 갱신 주기마다 회전, 우선순위 빈도)를 본다.
- 시나리오 ↔ XCUITest 파일 대응(매칭·예외·구현 대기·공백)은 이 문서가 아니라
  `doc-tracker/` 최신 월 파일의 「e2e 매핑」 절에서 판정한다.
- 시나리오 번호는 식별자(`test-widget.md#시나리오 N`)의 일부다. 중간 삽입하지 말고 끝에 덧붙인다.

## 테스트 시나리오

### 시나리오 1: 위젯 하나에 다섯 정보 영역이 함께 보인다
- **사전 조건**: 로그인된 상태. 다짐 문장 1개 이상, 오늘 이후 캘린더 일정 1개 이상, 미확인 메일 1통 이상,
  앱이 발행한 알림 1개 이상이 있음. 위치·캘린더 권한 허용.
- **실행 단계**:
  1. 홈 화면 편집에서 PocketAide 위젯(Large)을 추가한다.
  2. 위젯 전체를 본다.
- **기대 결과**:
  - 위젯 1개 안에 날씨·다음 일정·오늘의 다짐·메일·알림 다섯 영역이 모두 라벨과 함께 보인다.
  - 다섯 영역 모두 자리표시가 아니라 실제 정보를 담고 있다(각 영역 내용은 시나리오 2~6에서 검증).
  - 영역끼리 구분선으로 나뉘어 한눈에 구별된다.
- **검증 AC**: AC1
- **구현 상태**: 부분 구현 — 다섯 영역의 자리·라벨·구분선은 있으나, 실제 정보는 다짐·다음 일정·알림 영역만 표시된다.
  나머지 두 영역(날씨·메일)은 「곧 추가」 문구다. (2026-10-04 갱신 — 다음 일정·알림 영역 구현, 이전에는 네 영역이 자리표시)
- **관련 코드 테스트**: 없음

### 시나리오 2: 다가오는 캘린더 일정이 위젯에 나타난다
- **사전 조건**: 로그인된 상태. 위젯(Large) 추가됨. 캘린더 권한 허용.
- **실행 단계**:
  1. iOS 캘린더 앱에 오늘 이후 일정 4개를 추가한다(시작 시각이 서로 다르게).
  2. 위젯 갱신을 기다린 뒤 다음 일정 영역을 본다.
  3. 가장 가까운 일정을 삭제하고, 다시 갱신을 기다린다.
  4. 캘린더 권한을 거부한 상태에서 위젯을 본다.
- **기대 결과**:
  - 2단계: 시작 시각이 가까운 순서로 일정 1~3개가 제목·시각과 함께 보인다. 4번째 일정은 보이지 않는다.
  - 3단계: 삭제한 일정이 빠지고 다음 일정이 올라온다.
  - 4단계: 일정 대신 권한이 필요하다는 안내가 보인다.
- **검증 AC**: AC2
- **구현 상태**: 구현됨 — 위젯이 EventKit 으로 기기의 모든 캘린더에서 7일 안의 일정(진행 중 포함)을 읽어 시작 시각
  순으로 최대 3개를 제목·시각과 함께 보이고, 나머지는 「+ N 더」로 센다. 캘린더 권한이 있으면 30분마다 다시 읽어 삭제가
  갱신 주기 한 번 안에 반영된다. 권한이 없거나 거부되면 「앱에서 캘린더 접근을 허용해 주세요.」가 보인다. 권한은 로그인된
  앱이 시작될 때 한 번 요청한다. (2026-10-04 — 이전에는 미구현: 자리표시 「곧 추가」)
- **관련 코드 테스트**: `ios/PocketAideUnitTests/UpcomingEventsTests.swift` — `testShowsNearestThreeInStartOrder`, `testDeletedNearestLetsNextMoveUp`, `testEndedEventsAreDroppedAndOngoingKept`, `testEventsBeyondLookaheadAreExcluded`, `testLabels`

### 시나리오 3: 미확인 메일 요약이 위젯에 나타난다
- **사전 조건**: 로그인된 상태. 위젯(Large) 추가됨. 메일 계정이 연결되어 있음.
- **실행 단계**:
  1. 연결된 메일 계정으로 새 메일 2통을 보낸다.
  2. 위젯 갱신을 기다린 뒤 메일 영역을 본다.
  3. 메일 한 통을 읽음 처리하고, 다시 갱신을 기다린다.
- **기대 결과**:
  - 2단계: 미확인 메일 요약(예: 개수와 최신 메일의 발신자·제목)이 보인다.
  - 3단계: 요약이 읽음 처리를 반영한다(개수 감소 등).
  - 미확인 메일이 0통이면 빈 상태가 명확히 표시된다.
- **검증 AC**: AC3
- **구현 상태**: 미구현 — 메일 영역은 자리표시(「곧 추가」)다.
- **관련 코드 테스트**: 없음
- **비고**: 메일 계정 연결 방식(어느 서비스·어떤 인증)과 요약 표시 형태가 PRD에 정해져 있지 않다(AC3은 형태를 디자인에
  맡김). 사전 조건의 「연결된 메일 계정」과 기대 결과의 요약 형태는 연결 방식이 정해지면 구체화한다.

### 시나리오 4: 현재 위치의 날씨가 위젯에 나타난다
- **사전 조건**: 로그인된 상태. 위젯(Large) 추가됨.
- **실행 단계**:
  1. 위치 권한을 허용한 상태에서 날씨 영역을 본다.
  2. 같은 시각 iOS 날씨 앱(같은 위치)과 비교한다.
  3. 위치 권한을 거부한 상태에서 날씨 영역을 본다.
- **기대 결과**:
  - 1단계: 현재 기온, 날씨 상태, 강수 가능성이 보인다.
  - 2단계: 기온·상태가 날씨 앱과 크게 다르지 않다(같은 갱신 주기 안).
  - 3단계: 설정된 위치의 날씨가 보이거나, 위치 설정이 필요하다는 안내가 보인다.
- **검증 AC**: AC4
- **구현 상태**: 미구현 — 날씨 영역은 자리표시(「곧 추가」)다.
- **관련 코드 테스트**: 없음

### 시나리오 5: 다짐 영역은 갱신 주기마다 우선순위에 따라 회전한다
- **사전 조건**: 로그인된 상태. 위젯(Large) 추가됨. 다짐 문장이 우선순위 「높음」「보통」「낮음」 각 1개씩 있음.
- **실행 단계**:
  1. 다짐 영역의 문장을 기록한다.
  2. 갱신 주기(30분)마다 다짐 영역의 문장을 기록하기를 충분히 오래(예: 하루) 반복한다.
     (또는 같은 풀로 위젯 타임라인 엔트리를 충분히 많이 생성해 센다.)
  3. 같은 갱신 주기 안에서 홈 화면을 여러 번 오간다.
  4. 다짐 문장을 모두 지운 상태, 로그아웃한 상태에서 각각 위젯을 본다.
- **기대 결과**:
  - 2단계: 주기가 바뀔 때 문장이 바뀌는 경우가 있고, 관측 기간 동안 세 문장이 모두 한 번 이상 나타난다.
  - 2단계: 노출 횟수가 「높음」 > 「보통」 > 「낮음」 순서다.
  - 3단계: 같은 주기 안에서는 문장이 바뀌지 않는다.
  - 4단계: 문장이 없으면 「다짐을 앱에 등록해보세요.」, 로그아웃이면 「앱에서 로그인이 필요해요.」가 보인다.
- **검증 AC**: AC5
- **구현 상태**: 구현됨 — 30분 간격 엔트리 24개를 한 번에 만들고, 엔트리마다 시각을 시드로 앱과 같은
  `RotationSelector`(가중 추첨)로 고른다.
- **관련 코드 테스트**: `ios/PocketAideUnitTests/RotationSelectorTests.swift` — `testWeightedDistribution`, `testSameSeedIsDeterministic`, `testEmptyPoolReturnsNil`
- **비고**: 연속한 두 주기가 우연히 같은 문장을 뽑을 수 있으므로 「주기마다 반드시 다른 문장」은 기대 결과가 아니다.
  분포 단정은 난수에 기대므로 UI 수준에서 검증하려면 시드 고정(모킹 정책 `DET`)이 필요하다.

### 시나리오 6: 앱이 발행한 알림이 위젯에 모인다
- **사전 조건**: 로그인된 상태. 위젯(Large) 추가됨. 앱 알림 권한 허용.
- **실행 단계**:
  1. 앱이 알림을 발행하게 한다(예: PR 모니터의 CI 완료 푸시).
  2. 위젯 갱신을 기다린 뒤 알림 영역을 본다.
  3. 다른 앱(예: 메시지)의 알림을 받은 뒤 알림 영역을 본다.
- **기대 결과**:
  - 2단계: 앱이 발행한 알림이 요약(개수·최근 항목 등)으로 보인다.
  - 3단계: 다른 앱의 알림은 모이지 않으며, 위젯이나 앱 어딘가에 「이 앱이 보낸 알림만 모은다」는 점이 사용자에게 명시되어 있다.
- **검증 AC**: AC6
- **구현 상태**: 구현됨 — 위젯이 30분마다 알림 이력을 가져와, 실제로 푸시된 알림(CI 완료 이벤트 중 현재 알림 설정이 허용하는
  것) 가운데 확인하지 않은 것의 최신 항목을 푸시 배너와 같은 제목·본문으로 보이고 나머지는 「+ N 더」로 센다. 라벨이
  「PocketAide 알림」이라 이 앱이 보낸 알림만 모은다는 것이 위젯에 명시된다. 다른 앱의 알림은 읽지 않는다. (2026-10-04 — 이전에는
  미구현: 자리표시 「곧 추가」)
- **관련 코드 테스트**: `ios/PocketAideUnitTests/WidgetNotificationsTests.swift` — `testLatestUnacknowledgedFirstAndRestCounted`, `testStartEventsAndAcknowledgedAreLeftOut`, `testFollowsNotificationSettings`, `testEmptyHistory`, `testPushTextMatchesBackendBanner`
- **비고**: 알림 모음의 정의(PRD-8 열린 질문)는 2026-10-04 「본 앱이 직접 발행한 알림으로 한정」으로 해소됐다(`prd-widget.md`
  결정 사항). 위 기대 결과는 그 결정과 같다.

### 시나리오 7: 위젯 정보가 정체되지 않는다
- **사전 조건**: 로그인된 상태. 위젯(Large) 추가됨. 다짐 문장이 3개 이상 있음.
- **실행 단계**:
  1. 위젯의 다짐 영역을 확인한다.
  2. 앱에서 다짐 문장 하나를 삭제하고 새 문장 하나를 추가한다.
  3. 갱신 주기(30분)가 한 번 지난 뒤, 이어서 몇 시간에 걸쳐 위젯을 다시 확인한다.
  4. 백엔드에 닿지 않는 상태(예: 비행기 모드)로 갱신 주기를 넘긴 뒤 위젯을 보고, 연결을 되살린다.
- **기대 결과**:
  - 3단계: 갱신 주기 한 번 안에 삭제한 문장이 더 이상 나오지 않고, 새 문장이 회전 후보에 들어간다.
  - 4단계: 오류 중에는 「잠시 후 다시 시도할게요.」가 보이고, 연결이 되살아나면 이후 갱신에서 정상 표시로 돌아온다.
  - (다른 네 영역이 구현되면) 각 영역도 같은 갱신 주기로 새 정보를 가져온다. 다음 일정 영역은 캘린더 권한이 있으면
    30분마다 캘린더를 다시 읽는다(2026-10-04 구현).
- **검증 AC**: AC7
- **구현 상태**: 구현됨 — 앱에서 다짐을 추가·편집·삭제하거나 로그인·로그아웃하면 위젯 타임라인을 즉시 다시 요청한다
  (`WidgetRefresher.reloadAll`). 그 밖에는 문장 목록을 타임라인을 만들 때 한 번 가져와 30분 간격 엔트리 24개에 나눠 넣고,
  30분 뒤 다시 가져온다(알림 영역의 신선도를 위해 2026-10-04부터 — 이전에는 마지막 엔트리 뒤, 약 11.5시간 후).
  오류 시에는 60분 뒤 재시도한다. 즉시 재요청은 iOS 위젯 갱신 예산 안에서 처리되므로 반영 시점은 시스템이 정한다.
  (2026-10-01 정정 — 작성 시에는 「부분 구현」: 재요청 호출이 없어 삭제한 문장이 최대 약 11.5시간 남았다.)
- **관련 코드 테스트**: 없음
- **비고**: PRD-8 AC7은 갱신 간격을 수치로 정하지 않는다. 여기서는 구현이 스스로 정한 갱신 주기(30분)를 신선도의 기준으로
  삼았다. 「데이터 신선도 30분」과 「표시 회전 30분 + 데이터 약 12시간」 중 어느 쪽을 요구로 볼지 결정이 필요하다.

### 시나리오 8: 위젯의 각 영역을 누르면 앱의 해당 화면으로 들어간다
- **사전 조건**: 로그인된 상태. 위젯(Large) 추가됨. 앱이 다짐이 아닌 탭(예: 회사)을 마지막으로 연 상태로 백그라운드에 있음.
- **실행 단계**:
  1. 위젯의 다짐 영역을 누른다.
  2. 앱을 다른 탭으로 옮기고 홈 화면으로 나간 뒤, 날씨·다음 일정·메일·알림 영역을 차례로 하나씩 누른다
     (매번 앱을 다른 탭에 두고 나간다).
  3. 앱이 완전히 종료된 상태에서 1단계를 반복한다.
- **기대 결과**:
  - 1·3단계: 앱이 열리며 다짐 탭이 선택된다.
  - 2단계: 각 영역을 누르면 그 정보에 대응하는 앱 화면으로 들어간다. 마지막으로 연 탭에 그대로 머물지 않는다.
- **검증 AC**: AC8
- **구현 상태**: 부분 구현 — 다짐 영역은 `pocketaide://affirmations`로 다짐 탭에, 알림 영역은 `pocketaide://pr-monitor`로
  PR 모니터 탭에 진입한다(2026-10-04). 나머지 세 영역(날씨·다음 일정·메일)은 위젯 전체의 기본 링크 `pocketaide://root`를
  따르는데, 앱이 이 링크를 처리하지 않아 마지막으로 연 탭에 머문다.
- **관련 코드 테스트**: 없음
- **비고**: 앱에는 캘린더·메일·날씨 전용 화면이 없고, PRD-8도 세 영역의 진입 대상을 정하지 않았다. 대상이 정해지기
  전까지 2단계의 「대응하는 앱 화면」은 그 세 영역에 대해 판정할 수 없다. 알림 영역의 대상(PR 모니터 탭)은 `prd-widget.md`
  결정 사항에 있다.
