# PRD: 승인 게이트 (gatekeeper 통합)

## 달성 가치
- **V9**: 개발 워크플로우 인지 부하 감소 — 범위의 「결정」. 자동화가 실행 전에 구하는 허락을 폰에서 받아 곧바로 승인·거절하고, 기한 안에 결정되지 않은 요청은 만료시켜 침묵이 승인으로 해석되지 않게 한다. 범위의 「알림」(AC16·AC17) — 같은 호출자가 결정이 필요 없는 상태 변화를 폰 푸시로 알리고, 보낸 알림은 누가 보냈는지와 함께 앱에 남는다.

**가치 해석 노트**: AC13·AC14·AC15(호출자 키 발급·폐기, k8s ServiceAccount 호출자 등록)는 V9 「범위 밖」의 "자동화 자체의 설정·운영"이 아니라, 누가 사용자에게 허락을 구할 수 있는지를 통제하는 결정 경로의 일부로 본다. AC16(호출자의 단순 푸시 알림)은 「결정」이 아니라 V9 범위의 「알림」에 해당한다 — 자동화가 결정이 필요 없는 상태 변화(작업 완료·실패 등)를 사용자가 찾으러 가기 전에 알린다. 같은 호출자 인증(AC13~AC15)으로 누가 사용자에게 알림을 보낼 수 있는지를 통제하므로 이 PRD에 둔다. AC17(알림 기록)은 그 통제의 사후 확인이다 — 어떤 호출자가 누구를 대신해 무엇을 보냈는지를 사용자가 되짚을 수 있다.

## 개요

별도 서비스로 운영되던 [gatekeeper](https://github.com/dlddu/gatekeeper)(Go 백엔드 + Next.js PWA, Authelia forward-auth, Web Push)를 PocketAide로 흡수한다. 외부 자동화는 사용자가 발급한 호출자 키(클러스터 안의 자동화는 사용자가 등록한 k8s ServiceAccount의 토큰, AC15)로 PocketAide 백엔드에 승인 요청을 만들고 결과를 폴링하며, 키 소유자는 iOS 앱에서 APNs 푸시로 요청을 받아 결정한다.

```
외부 자동화 ──(호출자 키)──► pocket-aide 백엔드 ──(APNs)──► iOS 앱
 (CI·에이전트)   요청 생성 / 상태 폴링        │                 대기 목록 · 상세 · 결정
                                             └── OIDC 사용자 ◄── 승인·거절 (OIDC Bearer)
```

이 PRD가 해결하려는 문제는 두 가지다. 첫째, 자동화가 사람의 승인을 기다리는 동안 사용자가 자리에 없으면 작업이 멈춘다. 둘째, 승인 도구가 PocketAide와 별개의 PWA·인증 체계·푸시 채널로 떨어져 있어 알림과 결정 경험이 분산된다.

### 전제 (gatekeeper 레포 확인 결과, 2026-09-29 `762fafe` 기준)

| 항목 | gatekeeper의 현재 동작 | 본 PRD에서의 처리 |
|------|------------------------|------------------|
| 호출자 API | `POST /api/requests`, `GET /api/requests/{id}`, `x-api-key` 헤더 | 새 경로·스키마로 재정의 (아래 "호출자 API 계약") — **호환 없음** |
| 요청 생성 인증 | `x-api-key` 단일 시크릿(환경변수, 모든 호출자 공유) | 호출자별 키로 교체. 앱에서 발급·폐기 (AC1, AC13, AC14) |
| 요청 목록 `GET /api/requests` | **인증 없음**, 전체 요청 반환 | 제거. 목록은 OIDC 뒤의 앱 전용 경로로만 (AC2) |
| 사용자 인증 | Authelia forward-auth (`Remote-User` 헤더) | PocketAide OIDC 미들웨어 (`sub` 기준) |
| 수신 사용자 지정 | 생성 body의 `userId` = gatekeeper 내부 cuid. 생략 가능 | 필드 제거. 요청에 쓰인 호출자 키의 소유자가 수신자 (AC2) |
| 수신자 미지정 요청 | 푸시 없음, 자동 응답 없음, 모든 사용자에게 보임 | 존재하지 않음 — 모든 요청은 키 소유자에게 귀속 |
| 만료 | 조회 시점에만 lazy하게 `EXPIRED` 전환 | 같은 방식(조회 시 판정)을 유지하되 모든 경로에 일관되게 적용 (AC4) |
| 만료 요청 처리 | 승인·거절 처리가 `EXPIRED`를 막지 않음 → **만료된 요청도 승인 가능** | 409로 거부 (AC4) — **동작 변경** |
| 자동 응답 | `NONE` / `AUTO_APPROVE` / `AUTO_REJECT`, 사용자 단위 | 유지 + 자동 처리 여부를 이력에 구분 표시 (AC8, AC9) |
| 푸시 | VAPID Web Push, 본문 = `context` 전문 | 기존 APNs 경로(PRD-10)로 교체, 본문은 키 이름 + `context` 앞부분 (AC10) |
| 결정 UI | 상세 화면 승인/거절 + 확인 다이얼로그 | 유지 (AC7) + 잠금화면 알림 액션 신규 (AC11) |
| 저장소 | SQLite (`User`, `Request`, `PushSubscription`) | PocketAide DB에 새 마이그레이션. 기존 데이터는 이관하지 않음 (운영 노트) |

### 호출자 API 계약

gatekeeper 형식과 호환하지 않고 새로 정의한다. 기존 호출자는 전환 시 클라이언트를 수정한다(운영 노트 "전환 절차").

| 동작 | 경로 | 인증 | 요청 | 응답 |
|------|------|------|------|------|
| 요청 생성 | `POST /api/external/approvals` | `Authorization: Bearer <호출자 키 또는 k8s SA 토큰>` | `externalId`(필수), `context`(필수), `requesterName`(선택, 표시용), `sessionId`(선택, 표시용), `reason`(선택, 표시용), `timeoutSeconds`(선택) | 201 `{id, status, decisionMode, createdAt, expiresAt}` |
| 결과 조회 | `GET /api/external/approvals/{id}` | 같음 | - | 200 `{id, externalId, status, decisionMode, createdAt, expiresAt, processedAt}` |
| 단순 알림 (AC16) | `POST /api/external/notifications` | 같음 | `title`(필수, 120자 이하), `body`(선택), `requester`(선택, 200자 이하 — AC17) | 200 `{devices, sent}` |

- `/api/external/` 아래는 호출자 키만, 그 밖의 `/api/`는 OIDC만 받는다. 인증 경계를 경로로 구분한다.
- 수신자 필드는 없다. 알 수 없는 필드(예: 옛 `userId`)가 오면 400으로 거부해, 옛 클라이언트 설정이 섞여 들어오는 것을 전환 중에 바로 드러낸다.
- `sessionId`·`reason`(2026-10-25)은 둘 다 문자열이고 앞뒤 공백을 걷은 뒤 빈 문자열이면 보내지 않은 것과 같다. 걷은 뒤 `sessionId`는 최대 128자, `reason`은 최대 2000자(유니코드 문자 수)이고 넘으면 400이다. `sessionId`는 요청을 낸 session-platform 세션의 id, `reason`은 에이전트가 쓴 「이 호출을 하려는 이유」(한국어 한두 문장)다. 둘 다 상세 화면 표시용이며 인가·판정에 쓰지 않는다 — 판정 근거는 여전히 `context` 전문이다. 응답 형태는 바뀌지 않는다.
- `sessionId`가 있으면 서버가 생성 시점에 session-platform control-plane `GET /api/v1/sessions/{id}`로 세션 제목(`name`)을 조회해 요청과 함께 저장한다 — 세션이 나중에 지워져도 승인 기록에 제목이 남는다. 조회는 2초 타임아웃이고, 실패·404·타임아웃은 요청 생성을 실패시키지 않는다(제목 없이 저장). 앱용 JSON(`/api/approvals` 목록·상세·이력·결정 응답)에는 `session_id`·`session_name`·`reason`이 붙는다(값이 없으면 빈 문자열).
- `externalId`는 같은 호출자 키 안에서 유일하다(키가 다르면 같은 값을 써도 충돌하지 않는다).
- 상태 값은 gatekeeper와 같은 `PENDING` / `APPROVED` / `REJECTED` / `EXPIRED`를 쓴다.
- `decisionMode`는 처리 방식이다 — `manual`(사용자 결정) / `auto`(자동 응답) / `expired`(만료), 아직 `PENDING`이면 `null`. 앱의 처리 이력(AC8)이 쓰는 값과 같다. 자동 응답 모드(AC9)로 생성 즉시 처리된 요청은 생성 응답부터 `auto`다.
- 인증 수단은 둘이다. 호출자 키(`pak_`로 시작, AC13)와, 사용자가 등록한 k8s ServiceAccount의 projected 토큰(audience `pocket-aide`, AC15). 어느 쪽이든 요청은 그 호출자를 등록한 사용자에게 귀속되고 `externalId`의 유일성 범위도 그 호출자 안이다.

## 사용자 시나리오 (대표)

1. 점심 중 "승인 요청: prod 배포 v1.42" 푸시 → 알림 탭 → 상세에서 내용과 남은 시간(4분 12초) 확인 → 승인 → 확인 다이얼로그 → CI가 다음 폴링에서 `APPROVED`를 받아 배포를 진행한다.
2. 운전 중이라 결정하지 못함 → 10분 후 요청 만료 → 에이전트는 `EXPIRED`를 받고 중단한다. 나중에 앱을 열면 이력에 "만료"로 남아 있고, 승인 버튼은 없다.
3. 잠금화면에서 알림을 길게 눌러 "거절"을 바로 선택 → 앱을 열지 않고 처리된다. "승인"을 누르면 Face ID로 잠금 해제를 먼저 요구한다.
4. 새 CI 파이프라인을 붙이며 설정에서 "infra-ci" 키를 발급받아 한 번만 보이는 키 원문을 CI 시크릿에 넣는다. 몇 주 뒤 로그에 키가 찍힌 것을 발견하고 앱에서 그 키만 폐기한다 → 다른 호출자는 영향 없이 계속 동작하고, infra-ci만 새 키를 받아 교체한다.
5. 휴가 전 설정에서 자동 응답을 "자동 거절"로 바꿔 둔다 → 대기 탭 상단에 "자동 거절 모드 켜짐" 배너가 상시 보인다 → 복귀 후 이력에서 "자동 거절"로 표시된 요청들을 훑어본다.

## Acceptance Criteria

### AC1: 외부 자동화의 승인 요청 생성 (호출자 키 인증)
- **설명**: 백엔드는 외부 자동화용 요청 생성 엔드포인트를 노출하고, 이를 OIDC와 분리된 호출자 미들웨어 뒤에 둔다. 호출자 자격 증명은 AC13으로 발급된 호출자 키 또는 AC15로 등록된 k8s ServiceAccount의 토큰이고, 폐기(AC14)되지 않은 것만 유효하며, gatekeeper식 단일 공유 시크릿은 두지 않는다. 요청 형식은 위 "호출자 API 계약"을 따른다. 필수 필드 누락·알 수 없는 필드·선택 필드 `sessionId`(128자)·`reason`(2000자) 길이 초과는 400, 같은 키 안에서 `externalId` 중복은 409, 키 누락·불일치·폐기(SA 토큰은 미등록·폐기·검증 실패)는 401이다. 호출자 자격 증명은 요청 생성(AC1)과 상태 조회(AC3) 두 경로에만 유효하며, 앱용 목록·상세·결정 경로에는 쓸 수 없다. 반대로 OIDC 토큰으로는 요청을 생성할 수 없다.
- **달성 가치**: V9
- **검증 방법**: 유효 키로 생성 → 201 + `PENDING`. 같은 키로 동일 `externalId` 재생성 → 409, 다른 키로는 201. `userId` 필드를 넣어 생성 → 400. 129자 `sessionId`·2001자 `reason` → 400, 앞뒤 공백만 있는 두 필드 → 201(없는 것과 같다). 키 없이 → 401. 호출자 키로 앱 목록 경로 호출 → 401. OIDC 토큰으로 생성 경로 호출 → 401. SA 토큰 경로는 AC15에서 검증한다.

### AC2: 요청 소유권과 비공개
- **설명**: 모든 요청은 생성에 쓰인 호출자 키의 소유자(AC13) 한 명에게 귀속되며, 호출자가 수신자를 따로 지정하는 방법은 없다. 앱의 목록·상세·결정 경로는 OIDC 인증된 요청자 소유 요청으로 한정되며, 타인 소유 요청 id로의 접근은 존재 여부를 드러내지 않도록 404로 응답한다. 인증 없이 요청 목록이나 내용을 조회할 수 있는 경로는 존재하지 않는다(gatekeeper의 공개 `GET /api/requests`는 옮기지 않는다).
- **달성 가치**: V9
- **검증 방법**: A의 키로 만든 요청이 A의 목록에만 있고 B의 목록에 없는지 확인. B가 A의 요청 id로 상세·승인·거절 시도 → 모두 404. 토큰 없이 목록 경로 호출 → 401. 라우트 목록에 무인증 목록 경로가 없는지 확인.

### AC3: 요청자의 결과 조회 (폴링)
- **설명**: 외부 자동화는 그 요청을 만든 호출자 키(또는 SA 호출자의 토큰)로 요청 id의 현재 상태(`PENDING` / `APPROVED` / `REJECTED` / `EXPIRED`), 처리 방식(`decisionMode`, 수동/자동/만료), 처리 시각, 만료 시각을 조회할 수 있다. 응답은 AC4의 만료 규칙을 반영한 **실제** 상태여야 한다(만료 시각이 지난 `PENDING`을 `PENDING`으로 돌려주지 않는다). 다른 호출자 키로 만든 요청은 존재 여부를 드러내지 않도록 404로 응답한다. 응답에는 처리자의 OIDC `sub`·이메일 등 사용자 식별 정보를 포함하지 않는다.
- **달성 가치**: V9
- **검증 방법**: 생성 직후 조회 → `PENDING`. 앱에서 승인 후 조회 → `APPROVED` + `processedAt`. `timeoutSeconds=5` 요청을 6초 후 조회 → `EXPIRED`. 키 A로 만든 요청을 키 B로 조회 → 404. 응답 JSON에 사용자 식별자가 없는지 확인.

### AC4: 만료의 일관성
- **설명**: 만료 시각이 지난 `PENDING` 요청은 어떤 경로(요청자 조회, 앱 목록, 앱 상세, 결정 시도)에서 관측되든 `EXPIRED`로 취급된다. 만료된 요청에 대한 승인·거절은 409로 거부되며 상태가 바뀌지 않는다. `timeoutSeconds`가 없는 요청은 만료되지 않는다. 만료된 요청은 대기 목록에서 사라지고 이력(AC8)에 "만료"로 남는다. 만료는 요청을 조회·처리하는 시점에 판정하며, 이를 위한 백그라운드 작업은 두지 않는다(결정 사항).
- **달성 가치**: V9
- **검증 방법**: 만료 시각이 지난 요청에 승인 API 호출 → 409 + 상태 `EXPIRED` 유지(gatekeeper 대비 동작 변경 회귀 테스트). 만료 직후 대기 목록에서 사라지고 이력에 "만료"로 나타나는지 확인. `timeoutSeconds` 없는 요청이 장시간 후에도 `PENDING`인지 확인.

### AC5: 대기 목록
- **설명**: 앱에 승인 요청 대기 목록이 있으며, 사용자 소유의 `PENDING` 요청을 최신순으로 보여준다. 각 항목에는 요청자 이름, `context` 요약, 생성 시각, 만료가 있는 경우 남은 시간이 표시된다. 대기 목록은 하단 탭 바에 항상 보이는 독립 "승인" 탭에 있으며(결정 사항), 대기 요청 수는 이 탭의 배지로 노출된다. 목록은 화면 진입·포그라운드 복귀·당겨서 새로고침 시 갱신된다.
- **달성 가치**: V9
- **검증 방법**: "승인" 탭이 "더 보기"가 아닌 하단 탭 바에 보이는지 확인. 요청 3건 생성 → 목록에 최신순 3건 + 배지 3. 하나 승인 → 목록 2건 + 배지 2. 백그라운드에서 신규 요청 생성 후 포그라운드 복귀 → 목록 반영 확인.

### AC6: 요청 상세와 만료 카운트다운
- **설명**: 상세 화면은 `context` 전문, 요청자 이름, 생성에 쓰인 호출자 키 이름(AC13), `externalId`, 생성 시각, 현재 상태를 보여준다. 호출자가 `sessionId`를 보냈으면 「세션」 행에 생성 시점에 조회해 둔 세션 제목을 보이고, 제목이 비었으면(조회 실패·이름 없는 세션) 「제목 없음 · <세션 id 앞 8자>」를 보이며, `sessionId`가 없으면 행 자체를 숨긴다. 호출자가 `reason`을 보냈으면 `context` 전문 위에 「에이전트 설명」 섹션으로 보이고, 에이전트가 쓴 검증되지 않은 문장임을 캡션(「에이전트가 작성 · 검증되지 않음」)으로 구분한다. `reason`이 없으면 섹션을 보이지 않는다. 대기 목록·처리 이력 항목과 푸시(AC10)는 이 두 값을 보이지 않는다(2026-10-25). 만료가 있는 `PENDING` 요청은 남은 시간을 초 단위로 실시간 표시하고, 0에 도달하면 서버 응답을 기다리지 않고 결정 버튼을 비활성화한 뒤 상태를 "만료"로 갱신한다. 이미 처리된 요청의 상세는 결정 결과·처리 시각·처리 방식(수동/자동)을 보여주고 결정 버튼을 표시하지 않는다.
- **달성 가치**: V9
- **검증 방법**: `timeoutSeconds=30` 요청 상세를 열고 카운트다운이 감소하는지, 0 도달 시 버튼이 비활성화되고 "만료"로 바뀌는지 확인. 처리된 요청 상세에 결정 버튼이 없는지 확인. `sessionId`·`reason`을 보낸 요청의 상세에 세션 제목과 「에이전트 설명」(캡션 포함)이 `context` 위에 보이는지, 세션 제목 조회가 실패한 요청은 「제목 없음 · <id 앞 8자>」로, 두 필드가 없는 요청은 세션 행·설명 섹션 없이 보이는지 확인.

### AC7: 승인·거절
- **설명**: 상세 화면에서 승인 또는 거절을 선택하면 확인 단계를 거쳐 결정이 확정된다. 결정은 처리자와 처리 시각을 기록하며 되돌릴 수 없다. 이미 처리된 요청(다른 기기·잠금화면 액션에서 먼저 처리된 경우 포함)에 대한 결정은 409로 거부되고, 앱은 현재 상태를 다시 불러와 "이미 처리됨"을 안내한다. 결정은 먼저 도달한 하나만 유효하다(동시 요청 시 두 번째는 409).
- **달성 가치**: V9
- **검증 방법**: 승인 → 확인 → `APPROVED` + 처리자·처리 시각 기록. 확인 단계에서 취소 → 상태 불변. 두 기기에서 거의 동시에 승인·거절 → 하나만 성공, 다른 쪽은 409 + 안내. 처리된 요청에 결정 API 재호출 → 409.

### AC8: 처리 이력
- **설명**: 앱은 사용자 소유의 처리된 요청(`APPROVED` / `REJECTED` / `EXPIRED`)을 처리 시각 역순으로 보여주며, 커서 기반으로 이어서 불러온다. 각 항목은 결과와 함께 **처리 방식**(수동 결정 / 자동 승인 / 자동 거절 / 만료)을 구분해 표시한다. 이력은 삭제되지 않는다.
- **달성 가치**: V9
- **검증 방법**: 수동 승인·자동 거절·만료 요청을 각각 만든 뒤 이력에 세 가지 처리 방식이 구분되어 역순으로 나타나는지 확인. 25건 이상에서 스크롤 시 중복·누락 없이 이어지는지 확인.

### AC9: 자동 응답 모드
- **설명**: 사용자는 설정에서 자동 응답 모드를 `없음` / `자동 승인` / `자동 거절` 중에서 고른다. 자동 모드에서 생성된 요청은 생성 즉시 해당 결과로 처리되고(요청자는 AC3에서 즉시 결과를 받는다), 푸시를 보내지 않으며, 이력에 자동 처리로 기록된다(AC8). 자동 모드가 켜져 있는 동안 대기 목록 상단에 현재 모드를 알리는 배너가 상시 노출되어, 사용자가 통제권을 넘겨 두었다는 사실을 잊지 않게 한다. 모드 변경은 이후 생성되는 요청에만 적용되며 이미 `PENDING`인 요청에는 소급하지 않는다.
- **달성 가치**: V9
- **검증 방법**: 자동 승인으로 바꾼 뒤 생성 → 즉시 `APPROVED` + 푸시 미발송 + 이력 "자동 승인". 배너 노출 확인. `PENDING` 요청이 있는 상태에서 자동 거절로 변경 → 기존 요청은 `PENDING` 유지.

### AC10: 신규 요청 푸시 (APNs)
- **설명**: 자동 모드가 아닌 사용자에게 요청이 생성되면, 백엔드는 PRD-10의 기기 토큰·APNs 경로로 수신자의 모든 등록 기기에 푸시를 보낸다. 알림 제목은 "승인 요청 · {키 이름}"(AC13의 키 이름)이고, 본문은 `context` 앞부분이다. 본문은 APNs 페이로드 한도(4KB) 안에 들도록 잘라내고, 잘렸으면 말줄임(…)으로 표시한다. 잠금화면에서 본문을 가릴지는 iOS "미리보기 표시" 설정에 맡기며 앱이 따로 제어하지 않는다. 푸시 발송은 요청 생성 응답을 지연시키거나 실패시키지 않으며, 무효 토큰은 정리된다. 알림을 탭하면 앱이 해당 요청의 상세(AC6)로 곧바로 진입한다(PRD-10 AC7과 같은 딥링크 라우팅). 알림 탭은 결정을 트리거하지 않는다.
- **달성 가치**: V9
- **검증 방법**: 요청 생성 → 등록 기기에 푸시 도달, 제목에 키 이름 표시. 10KB `context` 요청 → 푸시가 정상 발송되고 본문이 말줄임으로 끝나는지 확인. APNs 장애를 모사해도 생성 API가 201을 즉시 반환하는지 확인. 알림 탭 → 해당 요청 상세 도달 + 상태 `PENDING` 유지. 앱 미실행 상태에서도 동일하게 동작하는지 확인.

### AC11: 잠금화면 알림 액션
- **설명**: 승인 요청 푸시는 "승인"·"거절" 알림 액션을 제공해 앱을 열지 않고 결정할 수 있게 한다. "승인" 액션은 기기 잠금 해제(Face ID/암호)를 요구한다. "거절"은 안전한 방향의 결정이므로 잠금 상태에서도 실행된다. 액션 처리 결과는 알림 교체(또는 로컬 알림)로 사용자에게 알린다 — 성공 시 결과, 이미 처리됨·만료(409) 시 그 사유. 액션이 네트워크 오류로 실패하면 결정되지 않은 것으로 간주하고 실패를 안내한다(재시도로 결정을 자동 확정하지 않는다).
- **달성 가치**: V9
- **검증 방법**: 잠금 상태에서 "승인" 선택 → 잠금 해제 요구 → 해제 후 `APPROVED`. 잠금 상태에서 "거절" → 잠금 해제 없이 `REJECTED`. 만료된 요청의 알림에서 액션 → 결정되지 않고 "만료됨" 안내. 비행기 모드에서 액션 → 상태 불변 + 실패 안내.

### AC12: 빈·로딩·오류 상태
- **설명**: 대기 목록이 비어 있으면 "대기 중인 승인 요청이 없습니다"와 함께 현재 자동 응답 모드를 보여준다. 로딩 중에는 이전 목록을 유지한 채 진행 표시를 한다. 네트워크·서버 오류는 배너로 알리고 재시도를 제공하며, 오류 중에도 결정 버튼이 결정 성공처럼 보이는 상태로 바뀌지 않는다.
- **달성 가치**: V9
- **검증 방법**: 요청 0건 → 빈 상태 문구 + 모드 표시. 서버 중단 → 오류 배너 + 재시도. 결정 요청 중 서버 중단 → 결정 버튼이 원래 상태로 돌아오고 상태가 바뀌지 않았음을 안내.

### AC13: 호출자 키 발급
- **설명**: 사용자는 앱의 승인 게이트 설정에서 호출자 이름(예: `infra-ci`)을 붙여 호출자 키를 발급한다. 키 원문은 발급 직후 한 번만 표시되고 복사할 수 있으며, 서버는 원문을 저장하지 않는다(해시만 저장). 이후 키 목록에서는 이름, 원문 앞부분 몇 글자(식별용), 발급 시각, 마지막 사용 시각만 보인다. 키는 발급한 사용자 소유이며 다른 사용자의 키 목록에 나타나지 않는다. 같은 사용자 안에서 호출자 이름은 유일하다. 키로 생성된 요청에는 그 키가 기록되어, 상세(AC6)·이력(AC8)에서 호출자가 스스로 밝힌 `requesterName`과 별개로 실제 키 이름이 표시된다.
- **달성 가치**: V9
- **검증 방법**: 키 발급 → 원문 1회 표시, 화면을 벗어났다 돌아오면 원문을 다시 볼 수 없음. DB에 원문이 없는지 확인. 발급한 키로 요청 생성 → 201, 목록의 마지막 사용 시각 갱신. `requesterName`을 다른 이름으로 보낸 요청의 상세에 실제 키 이름이 함께 보이는지 확인. 같은 이름으로 재발급 → 거부. 다른 사용자의 키 목록에 보이지 않는지 확인.

### AC14: 호출자 키 폐기
- **설명**: 사용자는 키 목록에서 키를 폐기한다(확인 단계 포함). 폐기는 즉시 적용되어 그 키로의 요청 생성(AC1)과 상태 조회(AC3)가 401이 되며, 되돌릴 수 없다(필요하면 새로 발급한다). 폐기 시점에 그 키로 생성된 `PENDING` 요청은 자동으로 승인·거절되지 않고 대기 목록에 남아 사용자가 직접 결정한다. 이 요청들의 상세와 목록 항목에는 "폐기된 키로 생성됨" 경고가 표시된다. 폐기된 키는 목록에 폐기 시각과 함께 남아, 과거 요청의 출처를 추적할 수 있다. 다른 키는 영향을 받지 않는다.
- **달성 가치**: V9
- **검증 방법**: 키 A·B 발급 → A 폐기 → A로 생성·조회 → 401, B로 생성 → 201. 폐기 전 A로 만든 `PENDING` 요청이 대기 목록에 남아 있고 경고가 표시되는지, 자동 응답 모드(AC9)가 켜져 있어도 상태가 바뀌지 않는지 확인. 폐기 후 이력의 A 요청에 키 이름이 그대로 보이는지 확인.

### AC15: k8s ServiceAccount 호출자 등록
- **설명**: 사용자는 승인 게이트 설정에서 호출자 이름과 k8s ServiceAccount(`네임스페이스/이름`)를 적어 SA 호출자를 등록한다. 등록에는 키 원문이 없다 — 그 SA로 도는 파드가 마운트한 projected 토큰(audience `pocket-aide`)이 자격 증명이다. 백엔드는 클러스터의 TokenReview로 토큰을 검증해 SA를 확인하고, 폐기되지 않은 등록이 있을 때만 그 등록을 호출자로 인정한다. 한 SA는 동시에 한 등록에만 묶인다(다른 사용자의 등록 포함). SA 호출자는 호출자 키와 같은 목록에 나타나며, 원문 앞부분 대신 `네임스페이스/이름`을 보인다. 호출자 이름의 유일성(AC13), 요청 귀속(AC2), 키 이름 표시(AC6·AC10), 마지막 사용 시각, 폐기(AC14)는 호출자 키와 같다. 등록되지 않았거나 폐기된 SA의 토큰, audience가 `pocket-aide`가 아닌 토큰, 검증에 실패한 토큰은 401이다.
- **달성 가치**: V9
- **검증 방법**: `homelab-k3s-mcp/homelab-k3s-mcp`를 이름 `homelab-k3s-mcp`로 등록 → 목록에 이름과 `homelab-k3s-mcp/homelab-k3s-mcp`가 보이고 원문은 없다. 그 SA의 projected 토큰으로 생성 → 201, 등록한 사용자의 대기 목록에 나타나고 마지막 사용 시각이 갱신된다. 다른 사용자가 같은 SA를 등록 → 409. 등록하지 않은 SA의 토큰 → 401. 같은 SA의 기본 토큰(audience가 apiserver) → 401. 등록을 폐기 → 생성·조회 401, 폐기 전 대기 요청은 경고와 함께 남는다.

### AC16: 호출자의 단순 푸시 알림
- **설명**: 백엔드는 결정이 필요 없는 알림용 엔드포인트(`POST /api/external/notifications`)를 승인 요청과 같은 호출자 미들웨어 뒤에 노출한다. 호출자 키(AC13)와 SA 호출자(AC15)가 같은 자격 증명으로 쓰고, 폐기(AC14)·미등록·검증 실패는 401, OIDC 토큰으로는 부를 수 없다. 요청은 `title`(필수, 공백 제거 후 1~120자)과 `body`(선택), `requester`(선택, 공백 제거 후 200자 이하 — AC17)이며, 누락·초과·알 수 없는 필드(예: 수신자 지정)는 400이다. 수신자는 그 호출자를 등록한 사용자이고(AC2와 같은 귀속), 백엔드는 PRD-10의 기기 토큰·APNs 경로로 그 사용자의 모든 등록 기기에 제목·본문을 **그대로** 보낸다(승인 푸시처럼 키 이름을 붙이지 않는다). 본문은 APNs 페이로드 한도(4KB) 안에 들도록 잘라 말줄임(…)으로 표시한다. 발송은 동기로 하고 응답에 등록 기기 수(`devices`)와 APNs가 받은 수(`sent`)를 실어 호출자가 도달 여부를 안다 — 기기가 없으면 `{devices: 0, sent: 0}`이고 오류가 아니다. 무효 토큰은 정리된다. 서버에 APNs가 설정되지 않았으면 503이다. 발송 전에 알림을 기록하고(AC17), 기록하지 못하면 500으로 답하고 보내지 않는다 — 기록 없이 나가는 알림은 없다. 기기 목록을 읽지 못해 발송이 시작되지 않은 경우(500)에는 그 기록을 지운다. 알림을 탭하면 앱의 알림 기록 화면(AC17)이 열린다. 페이로드에는 딥링크 id 대신 `kind`=`external_notification` 표식만 싣고, 앱은 이 표식이 있으면 알림 기록 화면으로 보낸다. 승인 요청을 만들지 않으며 자동 응답 모드(AC9)의 영향도 받지 않는다.
- **달성 가치**: V9
- **검증 방법**: 키로 `{title, body}` 전송 → 200 + 키 소유자의 등록 기기 수만큼 푸시 도달, 제목·본문이 보낸 그대로, 다른 사용자의 기기에는 도달하지 않음, 키 목록의 마지막 사용 시각 갱신. `title`만 전송 → 200, 본문 없는 알림. `title` 누락·공백·121자, `requester` 201자, 알 수 없는 필드 → 400이고 발송·기록 없음. 키 없음·폐기 키·OIDC 토큰 → 401. 등록한 SA의 projected 토큰 → 200, 등록한 사용자에게 도달. 10KB `body` → 본문이 말줄임으로 끝나고 발송됨. 기기 0개 → 200 `{devices: 0, sent: 0}`. 기록 저장 실패 → 500, 푸시 없음. 알림 탭 → 앱이 열리고 알림 기록 화면에 그 알림이 맨 위에 있음, 승인 탭 대기 목록·이력에는 아무것도 생기지 않음.

### AC17: 알림 기록
- **설명**: 백엔드는 호출자 알림(AC16)을 보낸 그대로 사용자별로 저장하고, 앱은 그 기록을 최신순으로 보이는 「알림 기록」 화면을 둔다. 기록마다 **보낸 호출자**와 **요청 주체**를 남긴다. 보낸 호출자는 인증으로 정해진 등록 호출자(AC13 키 또는 AC15 SA)이므로 항상 있다 — 화면에는 등록 이름과 종류(「키」·「SA」)로 보이고, 이후 키를 폐기해도 기록은 그 이름으로 남는다. 요청 주체는 호출자가 누구를 대신해 보냈는지를 스스로 밝힌 값(`requester`, 예: homelab-k3s-mcp 도구를 부른 MCP 사용자 `jwt:<sub>`·GitHub 워크플로 `github_oidc:<레포/워크플로>`)이고, 호출자가 보내지 않았으면 「요청 주체 미상」으로 보인다(1단계 — 결정 사항 「요청 주체는 2단계로 필수화한다」). 각 행은 제목, 본문(있으면 최대 3줄), 보낸 호출자, 요청 주체, 받은 시각, 도달(「N/M 기기」, 기기가 없었으면 「등록된 기기 없음」)을 보인다. 화면에서 아직 확인하지 않은 알림은 「새 알림」 표시가 붙는다. 화면이 목록을 받으면 받은 것 중 가장 최신 알림까지를 확인 처리한다 — 화면이 열려 있는 동안 도착한 알림은 다음 조회까지 미확인으로 남는다. 진입 경로는 셋이다: 「더 보기」의 「알림 기록」 항목, 단순 알림 푸시 탭(AC16), 위젯의 「PocketAide 알림」 영역(PRD-8 AC6·AC8). 최신 50건을 먼저 보이고 끝까지 내리면 이전 기록을 더 불러온다. 기록이 없으면 「받은 알림이 없어요.」, 불러오기 실패는 다른 탭과 같은 오류 배너와 다시 시도를 보인다. 기록은 앱에서 지우지 않는다.
- **달성 가치**: V9
- **검증 방법**: 키 `infra-ci`로 `{title, body, requester: "jwt:user-123"}` 전송 → 알림 기록 맨 위 행에 제목·본문·「infra-ci · 키」·「jwt:user-123」·받은 시각·도달 수, 「새 알림」 표시. `requester` 없이 전송 → 「요청 주체 미상」. SA 호출자(AC15)로 전송 → 「<등록 이름> · SA」. 화면을 나갔다 다시 열면 앞서 본 행의 「새 알림」이 사라짐. 화면을 연 채 새 알림 전송 → 당겨서 새로고침 전까지 그 알림은 미확인, 새로고침하면 「새 알림」과 함께 나타남. 다른 사용자의 기록은 보이지 않음. 51건 이상 → 끝까지 내리면 이전 기록이 이어짐. 기록 0건 → 「받은 알림이 없어요.」. 백엔드 중단 → 오류 배너, 복구 후 다시 시도로 목록 표시. 「더 보기」 → 「알림 기록」, 단순 알림 푸시 탭, 위젯 알림 영역 탭이 모두 이 화면을 연다.

## 결정 사항

- **gatekeeper를 별도 서비스로 두지 않고 PocketAide 백엔드·iOS 앱으로 흡수한다.** 인증(OIDC)·푸시(APNs)·기기 토큰을 PRD-10과 공유해 운영 대상을 하나 줄인다.
- **가치는 V9의 「결정」 범위로 본다.** 처음에는 별도 가치(V10)를 신설했으나(2026-09-29), V9가 「맡기고 받아보는」 흐름 전체로 재서술되면서(#71) 자동화가 허락을 구하는 지점도 맡긴 작업의 일부로 보아, 별도 가치를 두지 않고 V9 범위에 「결정」을 더했다(2026-10-05). 결정은 되돌릴 수 없으므로 V9 비고대로 통제를 편의보다 우선한다 — 이 PRD의 확인 단계(AC7), 승인 액션의 잠금 해제(AC11), 만료 요청 결정 차단(AC4)이 그 적용이다.
- **공개 목록 경로는 옮기지 않는다.** PocketAide는 공용 도메인이므로 gatekeeper의 무인증 `GET /api/requests`를 그대로 옮기면 모든 승인 요청 내용이 외부에 노출된다.
- **만료된 요청은 결정할 수 없다(동작 변경).** gatekeeper는 만료 요청의 승인을 허용했으나, V9 「결정」 범위의 "침묵이 승인으로 해석되지 않는다"와 충돌하므로 409로 막는다. 기존 호출자 세 곳(homelab-k3s-mcp, session-platform, pure-agent)은 모두 `EXPIRED`를 받으면 폴링을 멈추므로 이 변경에 영향받지 않는다(2026-09-29 확인).
- **API 키는 호출자별로 발급·폐기한다.** gatekeeper의 단일 공유 시크릿은 하나가 새면 모든 호출자를 교체해야 하고, 어느 호출자가 보낸 요청인지 구분할 수 없다. 호출자별 키로 유출 시 그 키만 폐기하고, 요청 출처를 호출자가 밝힌 이름이 아니라 실제 키로 확인한다(AC13·AC14).
- **클러스터 안의 호출자는 k8s ServiceAccount 토큰으로 인증할 수 있다(AC15, 2026-10-16).** 같은 k3s 클러스터에서 도는 호출자(homelab-k3s-mcp)는 키 원문을 시크릿에 넣어 돌리는 대신 파드가 이미 가진 정체성을 쓴다. 새어 나갈 원문이 없고, 파드·SA가 지워지면 토큰도 곧바로 무효가 된다. SA와 사용자의 연결은 서버 설정이 아니라 앱에서 등록한다 — 누가 사용자에게 허락을 구할 수 있는지는 사용자가 통제한다는 AC13의 원칙을 그대로 따른다. 클러스터 밖 호출자는 계속 호출자 키를 쓴다.
- **SA 토큰은 TokenReview로 검증하고 audience `pocket-aide`를 요구한다.** 백엔드가 서명 키·issuer 설정을 따로 들고 있지 않아도 되고, 삭제된 파드의 토큰은 바로 거부된다. audience를 요구해 apiserver용 기본 토큰을 PocketAide로 보내거나 PocketAide로 보낸 토큰을 apiserver에 재사용하는 일을 막는다. 공용 도메인으로 들어오는 임의 토큰이 apiserver 부하가 되지 않도록, 서명 검증 전 `iss`가 클러스터 issuer와 같을 때만 TokenReview를 부르고 그 결과는 60초 캐시한다(호출자는 2초마다 폴링한다). 등록·폐기 조회는 캐시하지 않으므로 앱에서의 폐기는 즉시 적용된다.
- **한 SA는 한 등록에만 묶인다.** 같은 SA가 두 사용자에게 등록되면 요청 수신자를 정할 수 없다. 사용자 안의 호출자 이름 유일성과 별개로, 폐기되지 않은 등록 사이에서 SA는 전역으로 유일하다.
- **SA 호출자의 저장 형태(2026-10-16 구현으로 확정).** SA 호출자는 호출자 키와 같은 `approval_caller_keys` 행이고 `kind`(`key`/`k8s_sa`)와 `service_account`(`네임스페이스/이름`)로 구분한다 — 요청·이력·폐기·푸시가 키 id 하나로 그대로 이어진다. FK 가 걸린 테이블을 재생성하지 않으려고 `key_hash`·`key_prefix` 의 NOT NULL 을 유지하고, SA 행의 `key_hash` 는 어떤 키의 SHA-256 과도 겹칠 수 없는 `sa:` 채움값, `key_prefix` 는 빈 문자열이다. 앱용 API 는 같은 `POST /api/approval-keys` 에 `kind`=`k8s_sa`·`service_account` 를 보내 등록하고(응답에 `key` 없음), 목록 항목에 `kind`·`service_account` 가 붙는다. SA 토큰 검증 경로는 `K8S_CALLER_AUTH=true` 일 때만 켜지고, apiserver 에 닿지 못하면 503 이다(호출자 키 경로는 영향 없음).
- **외부 응답에 처리 방식(`decisionMode`)을 싣는다.** homelab-k3s-mcp의 이벤트 로그는 자동 승인을 따로 기록한다(gatekeeper의 `autoApproved` 대응). 처리 방식은 사용자 식별 정보가 아니므로 AC3과 충돌하지 않는다.
- **상세에 세션 제목과 에이전트 이유를 보인다(2026-10-25).** 승인 요청을 보고 「어느 세션의 어떤 작업에서 왜 나왔는지」를 `context` 전문만으로는 바로 알기 어렵다. 그래서 호출자 계약에 선택 필드 `sessionId`·`reason`을 더하고 상세(AC6)에만 보인다. 서버가 따로 만든 한글 「무엇을」 요약은 두지 않고 `context` 전문은 그대로 둔다. 목록·이력·푸시는 바꾸지 않는다 — 푸시 형식(AC10)은 그대로다.
  - **세션 제목은 생성 시점에 서버가 조회해 저장한다.** 호출자가 제목을 직접 보내게 하지 않는 것은 화면의 제목이 PocketAide 세션 화면에 보이는 것(session-platform `Session.name`)과 같아야 하기 때문이다. 상세를 열 때마다 조회하지 않고 저장하는 것은 세션이 지워진 뒤에도 승인 기록에 남기기 위함이다. 조회는 응답을 2초 넘게 늦추지 않고, 실패해도 요청은 만들어진다 — 승인 경로가 세션 플랫폼의 가용성에 묶이지 않게 한다. 저장은 `approval_requests`의 `session_id`·`session_name`·`reason`(셋 다 `TEXT NOT NULL DEFAULT ''`, 마이그레이션 `0016_approval_session_reason`)이다.
  - **두 값은 표시용이고 신뢰 경계 밖이다.** `sessionId`는 인증된 호출자가 붙인 표시용 값이며 인가 판단에 쓰지 않는다. minimax-code 세션 → helper 파드의 k3s-mcp-proxy → homelab-k3s-mcp 경로에서는 proxy 가 `X-Session-Platform-Session-Id` 헤더를 덮어써 워크로드가 위조할 수 없다. `reason`은 에이전트가 쓴 검증되지 않은 문장이라 상세에서 캡션으로 구분하고, 판정 근거는 여전히 `context` 전문이다.
  - **이번 범위는 minimax-code 경로만이다.** claude-code 세션(플러그인 직접 호출)과 approval-gated 세션 자체의 승인은 `sessionId`·`reason`을 보내지 않으며, 그 요청의 상세는 세션 행·설명 섹션 없이 이전과 같다.
- **폐기된 키의 대기 요청은 자동 처리하지 않는다.** 폐기는 대개 유출 의심 때문이므로 자동 승인은 위험하고, 자동 거절은 정상 요청까지 끊는다. 경고와 함께 사용자 판단에 맡긴다.
- **승인 액션만 잠금 해제를 요구한다.** 거절은 자동화를 멈추는 안전한 방향이므로 마찰을 두지 않는다.
- **수신자는 호출자 키의 소유자다.** 키가 사용자에게 귀속되므로(AC13) 요청에 수신자를 따로 적지 않는다. 수신자를 안 적은 요청이라는 경우 자체가 사라진다. 한 요청을 여러 사람에게 보내야 할 때 확장한다.
- **호출자 API는 gatekeeper와 호환하지 않고 새로 정의한다.** 호출자별 키 도입으로 호출자 설정을 어차피 모두 바꿔야 하므로, 이번에 PocketAide 경로 체계(`/api/external/…`)와 Bearer 인증으로 맞춘다. 대가로 세 호출자 레포의 클라이언트 코드·테스트·배포 설정을 수정한다.
- **gatekeeper는 병행 운영 후 종료한다.** 호출자 레포를 하나씩 옮기며 검증하고, 셋 다 옮긴 것이 확인되면 gatekeeper를 끈다. 전환 기간에는 승인 요청이 PWA와 앱 두 곳으로 나뉜다. homelab-k3s-mcp는 승인 서버에 닿지 못하면 게이트 걸린 쓰기를 거부하므로(fail-closed), 전환이 꼬여도 승인 없이 실행되는 일은 없다.
- **gatekeeper 데이터는 이관하지 않고 종료 시 삭제한다.** 사용자 매핑·이관 비용에 비해 과거 이력의 가치가 낮다. 백업도 남기지 않는다.
- **승인은 하단 탭 바에 보이는 독립 탭으로 둔다.** 대기 개수 배지가 보여야 하므로 "더 보기"에 두지 않고, PR 모니터와 묶지도 않는다. 대신 임시공간 탭을 "더 보기"로 옮긴다(임시공간의 입력은 주로 숏컷·위젯으로 들어온다). 탭 순서는 여정 mockup 작성 시 정한다. 이 이동으로 임시공간 미분류 배지가 하단 탭 바에서 보이지 않게 되는 것은 두 가지로 보완한다: PRD-4 AC5의 배지를 "더 보기" 목록 항목에 표시하도록 개정하고, 위젯에 미분류 개수를 추가한다(PRD-8 AC9).
- **푸시 본문은 키 이름 + `context` 앞부분이다.** 알림만으로 대략 판단할 수 있고 APNs 4KB 한도 안에 들어간다. 잠금화면 노출은 iOS 설정에 맡긴다(AC10).
- **만료는 조회 시점에 판정한다.** 사용자에게 보이는 결과(AC4)는 판정 방식과 무관하므로 가장 단순한 방식을 쓴다. 웹훅·만료 리마인드(후속 작업 1·2)를 도입할 때 백그라운드 정리를 함께 추가한다.
- **백엔드 1차의 세부 형태(2026-10-09 구현으로 확정).** 저장소는 `approval_caller_keys`·`approval_requests` 두 테이블이고, 만료된 요청은 상태를 `PENDING`으로 둔 채 읽을 때 `EXPIRED`로 보이며 그 처리 시각은 만료 시각이다. 키 원문은 `pak_` 접두 + 무작위 32바이트(base64url)이고 서버에는 SHA-256 해시와 식별용 앞 12자만 남는다. 호출자 이름의 유일성은 폐기되지 않은 키 안에서만 따진다 — 유출 키를 폐기하고 같은 이름으로 새로 받는 흐름(사용자 시나리오 4)을 막지 않기 위함이다. 요청 id 는 무작위 128비트(16진 32자)다. 앱용 경로는 `/api/approval-keys`(목록·발급, `/{id}/revoke` 폐기 — 폐기한 키도 목록에 남으므로 DELETE 가 아니다)와 `/api/approvals`(대기 목록·`/{id}` 상세·`/{id}/approve`·`/{id}/reject`)이고, 결정이 409 이면 응답에 현재 상태를 실어 앱이 다시 불러오지 않고도 「이미 처리됨」·「만료」를 안내할 수 있게 한다.

- **단순 알림은 승인 게이트의 호출자 경로를 그대로 쓴다(AC16, 2026-10-25).** homelab-k3s-mcp 처럼 이미 SA 호출자로 등록된 자동화가 시크릿·네트워크 설정 변경 없이 같은 토큰·같은 서비스 주소로 알림을 보낼 수 있다. 별도 「알림 키」를 두지 않으므로 등록된 호출자는 승인 요청과 알림을 모두 보낼 수 있다 — 권한 범위 분리는 후속 작업 3에서 함께 다룬다.
- ~~**단순 알림은 푸시만 하고 저장하지 않는다(AC16).** 앱 안의 이력 화면을 두면 마이그레이션·화면·읽음 처리가 따라오는데, 알림의 목적(찾으러 가기 전에 알려 준다)은 푸시만으로 충족된다. 필요해지면 PRD-10 알림 이력과 묶어 확장한다.~~ — 2026-10-27 대체: 아래 「단순 알림을 호출자와 함께 저장한다」.
- **단순 알림을 호출자와 함께 저장한다(AC17, 2026-10-27).** 푸시는 놓치거나 지우면 다시 볼 수 없고, 등록된 호출자가 늘면 어떤 자동화가 누구를 대신해 무엇을 보냈는지 되짚을 곳이 필요해졌다. 저장은 `external_notifications` 한 테이블이다(마이그레이션 `0017_external_notifications`) — 보낸 호출자는 `caller_key_id`(호출자 키·SA 공통 행, FK)로 남겨 화면의 이름·종류를 키 행에서 읽고, 요청 주체는 `requester` 문자열이다. 발송 **전에** 기록해 기록 실패가 곧 발송 거부가 되게 했다 — 호출자 기록을 필수로 하라는 요구를 「기록 없는 알림은 나가지 않는다」로 지킨다. PRD-10 알림 이력(CI 이벤트)과는 묶지 않는다: 그쪽은 레포·PR·커밋 그룹과 명시적 확인(PRD-10 AC12)이 핵심이고, 이쪽은 호출자가 정한 제목·본문뿐이라 같은 표에 섞으면 둘 다 빈 칸이 늘어난다.
- **보낸 호출자와 요청 주체를 구분한다(AC17).** 보낸 호출자는 PocketAide 가 인증으로 확인한 값이라 믿을 수 있지만, 그 호출자가 여러 사람·워크플로의 요청을 받아 대신 보내는 중계자(homelab-k3s-mcp)이면 그것만으로는 「누가」를 알 수 없다. 요청 주체는 중계자가 자기 인증 계층에서 확인한 값을 보고하는 것이라 PocketAide 는 검증할 수 없는 표시용 값이다 — 승인 요청의 `requesterName`·`sessionId` 와 같은 신뢰 경계로 다루고, 화면에서 보낸 호출자와 다른 줄로 보인다. homelab-k3s-mcp 는 도구 인자가 아니라 MCP 요청을 인증한 주체(이벤트 로그의 principal)를 보내므로 도구를 부르는 쪽이 값을 지어낼 수 없다.
- **요청 주체는 2단계로 필수화한다(AC17).** 호출자 API 는 알 수 없는 필드를 400으로 거부하므로, `requester` 를 처음부터 필수로 하면 PocketAide 배포와 homelab-k3s-mcp 배포 사이에 모든 알림이 실패하고, 반대 순서면 새 필드가 거부된다. 그래서 1단계에서는 선택 필드로 받고(없으면 빈 문자열 — 화면에서 「요청 주체 미상」), homelab-k3s-mcp 가 항상 보내게 된 뒤 2단계에서 필수로 바꾼다(후속 작업 7). 보낸 호출자는 처음부터 항상 기록된다.
- **알림 기록의 확인은 화면을 보는 것이다(AC17).** PRD-10 은 CI 알림마다 「확인」 버튼을 누르게 하지만(실패를 지나치지 않게), 단순 알림은 결정이 필요 없는 상태 변화라 버튼 하나를 더 누르게 할 이유가 약하다. 대신 화면이 받은 목록의 최신 id 까지만 확인 처리해, 화면을 연 채 새로 온 알림이 보지 않고 확인되는 일은 없게 한다. 이 확인 상태가 위젯 「PocketAide 알림」 영역(PRD-8 AC6)에 보일 알림을 정한다.
- **알림 기록은 별도 화면이고 「더 보기」에 둔다(AC17).** 승인 탭은 결정할 것이 쌓이는 곳이라 상태 변화 알림을 섞지 않는다. 하단 탭 바는 이미 다섯 칸이 차 있어(PRD-12 「승인은 하단 탭 바에…」), 자주 들르는 입구는 푸시 탭과 위젯이 맡고 탭 목록에는 「더 보기」 항목으로 둔다.
- **단순 알림의 제목은 호출자가 정한 그대로다(AC16).** 승인 푸시(AC10)는 "승인 요청 · {키 이름}"으로 출처를 박지만, 알림은 내용이 곧 목적이라 제목을 덮어쓰지 않는다. 호출자는 사용자가 직접 등록한 자동화뿐이므로 사칭 위험을 받아들인다.
- **단순 알림 페이로드에 `kind` 표식을 싣는다(AC16, 2026-10-25 정정 · 2026-10-27 목적지 변경).** 앱은 딥링크 id(`approval_id`·`event_id`)가 없는 푸시를 CI 푸시로 보고 PR 모니터로 보낸다 — 모든 푸시가 CI 푸시이던 때의 기본값이다. 처음 구현은 데이터 없이 보내 단순 알림 탭이 PR 모니터를 열었다(배포 후 실기기에서 발견). 기본값을 바꾸면 id 가 빠진 CI 푸시의 동작까지 바뀌므로, 단순 알림 쪽에 표식을 싣고 앱이 그 표식만 예외로 둔다. 표식을 모르는 이전 앱 버전에서는 업데이트 전까지 PR 모니터가 열린다. 알림 기록 화면(AC17)이 생기면서 표식이 있는 푸시의 탭은 「아무 데도 가지 않음」에서 「알림 기록 화면」으로 바뀌었다 — 페이로드는 그대로다.
- **단순 알림은 동기로 보내고 도달 수를 돌려준다(AC16).** 승인 요청은 생성 응답이 푸시에 막히면 안 되지만(AC10), 알림은 푸시가 곧 결과다. 호출자(MCP 도구 등)가 "기기 없음"·"발송 실패"를 구분해 사용자에게 되돌려 줄 수 있게 한다.

**전환 절차**

1. PocketAide에 승인 게이트를 배포한다(gatekeeper는 계속 운영).
2. 레포마다: 앱에서 호출자 키를 발급 → 클라이언트를 새 API 계약으로 수정(경로, Bearer 인증, `userId` 제거) → 시크릿 교체 → 실제 요청 1건으로 앱 수신·결정·폴링 확인.
3. 세 레포 전환 확인 후 gatekeeper(Next.js PWA·Web Push·Authelia 연동, flux-cd-apps 배포)를 내리고 SQLite 데이터를 삭제한다. 관련 ExternalSecret·SSM 파라미터도 정리한다.

**선택 필드 배포 순서 (`sessionId`·`reason`, 2026-10-25)**

1. PocketAide를 먼저 배포한다. 새 필드를 모르는 PocketAide에 보내면 알 수 없는 필드라 400이 되고, homelab-k3s-mcp 는 fail-closed 라 게이트 걸린 쓰기가 막힌다. 마이그레이션 `0016` 이 함께 나간다(`docs/review-policy.md` MA1 — 사람 승인).
2. homelab-k3s-mcp 를 배포한다(두 필드를 값이 있을 때만 보낸다).
3. session-platform(k3s-mcp-proxy 의 헤더 추가)은 언제 나가도 무해하다 — 모르는 헤더는 homelab-k3s-mcp 가 무시한다.

PocketAide 쪽에 새 설정은 없다. 세션 제목 조회는 세션 화면이 이미 쓰는 `SESSION_PLATFORM_URL`(기본 `http://control-plane.session-platform.svc.cluster.local`)을 그대로 쓴다.

**알림 요청 주체 배포 순서 (`requester`, 2026-10-27)**

1. PocketAide를 먼저 배포한다. 마이그레이션 `0017` 이 함께 나간다(`docs/review-policy.md` MA1 — 사람 승인). 이 시점부터 알림이 기록되고, homelab-k3s-mcp 가 보낸 알림은 「요청 주체 미상」으로 남는다.
2. homelab-k3s-mcp 를 배포한다(`requester` 에 MCP 요청의 principal 을 항상 싣는다). 순서가 뒤집히면 새 필드를 모르는 PocketAide 가 400으로 거부해 그 사이 알림이 실패한다.
3. 2단계(후속 작업 7): homelab-k3s-mcp 배포를 확인한 뒤 PocketAide 에서 `requester` 를 필수로 바꾼다. 다른 호출자가 알림을 보내고 있다면 그 호출자도 먼저 `requester` 를 싣게 한다.

## 열린 질문

- **pure-agent 처리**: 최근 활동이 없는 호출자다. 새 API로 전환할지, 전환 대신 gatekeeper 의존을 걷어낼지.
- **알림 기록 보존 기간 (AC17)**: 지금은 지우지 않는다. 알림이 많아져 목록·DB 가 무거워지면 기간(예: 90일)을 둘지, 사용자가 지우게 할지.
