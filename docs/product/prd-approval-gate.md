# PRD: 승인 게이트 (gatekeeper 통합)

## 달성 가치
- **V10**: 자동화에 대한 즉시 승인 통제 — CI·배포·에이전트가 사람의 결정을 기다리는 요청을 폰에서 받아 곧바로 승인·거절하고, 기한 안에 결정되지 않은 요청은 명시적으로 만료시켜 침묵이 승인으로 해석되지 않게 한다.

## 개요

별도 서비스로 운영되던 [gatekeeper](https://github.com/dlddu/gatekeeper)(Go 백엔드 + Next.js PWA, Authelia forward-auth, Web Push)를 PocketAide로 흡수한다. 외부 자동화는 API 키로 PocketAide 백엔드에 승인 요청을 만들고 결과를 폴링하며, 사용자는 iOS 앱에서 APNs 푸시로 요청을 받아 결정한다.

```
외부 자동화 ──(x-api-key)──► pocket-aide 백엔드 ──(APNs)──► iOS 앱
 (CI·에이전트)   요청 생성 / 상태 폴링        │                 대기 목록 · 상세 · 결정
                                             └── OIDC 사용자 ◄── 승인·거절 (OIDC Bearer)
```

이 PRD가 해결하려는 문제는 두 가지다. 첫째, 자동화가 사람의 승인을 기다리는 동안 사용자가 자리에 없으면 작업이 멈춘다. 둘째, 승인 도구가 PocketAide와 별개의 PWA·인증 체계·푸시 채널로 떨어져 있어 알림과 결정 경험이 분산된다.

### 전제 (gatekeeper 레포 확인 결과, 2026-09-29 `762fafe` 기준)

| 항목 | gatekeeper의 현재 동작 | 본 PRD에서의 처리 |
|------|------------------------|------------------|
| 요청 생성 인증 | `POST /api/requests`, `x-api-key` 단일 시크릿 | 유지하되 OIDC와 분리된 별도 미들웨어 (AC1) |
| 요청 목록 `GET /api/requests` | **인증 없음**, 전체 요청 반환 | 제거. 목록은 OIDC 뒤의 앱 전용 경로로만 (AC2) |
| 사용자 인증 | Authelia forward-auth (`Remote-User` 헤더) | PocketAide OIDC 미들웨어 (`sub` 기준) |
| 수신 사용자 지정 | 생성 body의 `userId` = gatekeeper 내부 cuid. 생략 가능 | 수신자 식별 방식 재정의 (AC2, 열린 질문) |
| 수신자 미지정 요청 | 푸시 없음, 자동 응답 없음, 모든 사용자에게 보임 | 소유권 원칙상 허용하지 않거나 기본 수신자로 귀속 (열린 질문) |
| 만료 | 조회 시점에만 lazy하게 `EXPIRED` 전환 | 모든 경로에서 일관되게 만료로 취급 (AC4) |
| 만료 요청 처리 | 승인·거절 처리가 `EXPIRED`를 막지 않음 → **만료된 요청도 승인 가능** | 409로 거부 (AC4) — **동작 변경** |
| 자동 응답 | `NONE` / `AUTO_APPROVE` / `AUTO_REJECT`, 사용자 단위 | 유지 + 자동 처리 여부를 이력에 구분 표시 (AC8, AC9) |
| 푸시 | VAPID Web Push, 본문 = `context` 전문 | 기존 APNs 경로(PRD-10)로 교체 (AC10) |
| 결정 UI | 상세 화면 승인/거절 + 확인 다이얼로그 | 유지 (AC7) + 잠금화면 알림 액션 신규 (AC11) |
| 저장소 | SQLite (`User`, `Request`, `PushSubscription`) | PocketAide DB에 새 마이그레이션. 기존 데이터 이관 여부는 열린 질문 |

## 사용자 시나리오 (대표)

1. 점심 중 "승인 요청: prod 배포 v1.42" 푸시 → 알림 탭 → 상세에서 내용과 남은 시간(4분 12초) 확인 → 승인 → 확인 다이얼로그 → CI가 다음 폴링에서 `APPROVED`를 받아 배포를 진행한다.
2. 운전 중이라 결정하지 못함 → 10분 후 요청 만료 → 에이전트는 `EXPIRED`를 받고 중단한다. 나중에 앱을 열면 이력에 "만료"로 남아 있고, 승인 버튼은 없다.
3. 잠금화면에서 알림을 길게 눌러 "거절"을 바로 선택 → 앱을 열지 않고 처리된다. "승인"을 누르면 Face ID로 잠금 해제를 먼저 요구한다.
4. 휴가 전 설정에서 자동 응답을 "자동 거절"로 바꿔 둔다 → 대기 탭 상단에 "자동 거절 모드 켜짐" 배너가 상시 보인다 → 복귀 후 이력에서 "자동 거절"로 표시된 요청들을 훑어본다.

## Acceptance Criteria

### AC1: 외부 자동화의 승인 요청 생성 (API 키 인증)
- **설명**: 백엔드는 외부 자동화용 요청 생성 엔드포인트를 노출하고, 이를 OIDC와 분리된 API 키 미들웨어 뒤에 둔다. 필드는 `externalId`(필수, 전역 유일), `context`(필수), `requesterName`(필수), `timeoutSeconds`(선택, 양의 정수), 수신자 식별자(AC2)이다. 필수 필드 누락은 400, `externalId` 중복은 409, API 키 누락·불일치는 401이다. API 키는 요청 생성(AC1)과 상태 조회(AC3) 두 경로에만 유효하며, 앱용 목록·상세·결정 경로에는 쓸 수 없다. 반대로 OIDC 토큰으로는 요청을 생성할 수 없다.
- **달성 가치**: V10
- **검증 방법**: 유효 키로 생성 → 201 + `PENDING`. 동일 `externalId` 재생성 → 409. 키 없이 → 401. API 키로 앱 목록 경로 호출 → 401. OIDC 토큰으로 생성 경로 호출 → 401.

### AC2: 요청 소유권과 비공개
- **설명**: 모든 요청은 정확히 한 명의 수신 사용자에게 귀속된다. 앱의 목록·상세·결정 경로는 OIDC 인증된 요청자 소유 요청으로 한정되며, 타인 소유 요청 id로의 접근은 존재 여부를 드러내지 않도록 404로 응답한다(PRD-11 AC2와 같은 원칙). 인증 없이 요청 목록이나 내용을 조회할 수 있는 경로는 존재하지 않는다(gatekeeper의 공개 `GET /api/requests`는 옮기지 않는다).
- **달성 가치**: V10
- **검증 방법**: 사용자 A 수신 요청이 B의 목록에 없는지 확인. B가 A의 요청 id로 상세·승인·거절 시도 → 모두 404. 토큰 없이 목록 경로 호출 → 401. 라우트 목록에 무인증 목록 경로가 없는지 확인.

### AC3: 요청자의 결과 조회 (폴링)
- **설명**: 외부 자동화는 API 키로 요청 id의 현재 상태(`PENDING` / `APPROVED` / `REJECTED` / `EXPIRED`), 처리 시각, 만료 시각을 조회할 수 있다. 응답은 AC4의 만료 규칙을 반영한 **실제** 상태여야 한다(만료 시각이 지난 `PENDING`을 `PENDING`으로 돌려주지 않는다). 응답에는 처리자의 OIDC `sub`·이메일 등 사용자 식별 정보를 포함하지 않는다.
- **달성 가치**: V10
- **검증 방법**: 생성 직후 조회 → `PENDING`. 앱에서 승인 후 조회 → `APPROVED` + `processedAt`. `timeoutSeconds=5` 요청을 6초 후 조회 → `EXPIRED`. 응답 JSON에 사용자 식별자가 없는지 확인.

### AC4: 만료의 일관성
- **설명**: 만료 시각이 지난 `PENDING` 요청은 어떤 경로(요청자 조회, 앱 목록, 앱 상세, 결정 시도)에서 관측되든 `EXPIRED`로 취급된다. 만료된 요청에 대한 승인·거절은 409로 거부되며 상태가 바뀌지 않는다. `timeoutSeconds`가 없는 요청은 만료되지 않는다. 만료된 요청은 대기 목록에서 사라지고 이력(AC8)에 "만료"로 남는다.
- **달성 가치**: V10
- **검증 방법**: 만료 시각이 지난 요청에 승인 API 호출 → 409 + 상태 `EXPIRED` 유지(gatekeeper 대비 동작 변경 회귀 테스트). 만료 직후 대기 목록에서 사라지고 이력에 "만료"로 나타나는지 확인. `timeoutSeconds` 없는 요청이 장시간 후에도 `PENDING`인지 확인.

### AC5: 대기 목록
- **설명**: 앱에 승인 요청 대기 목록이 있으며, 사용자 소유의 `PENDING` 요청을 최신순으로 보여준다. 각 항목에는 요청자 이름, `context` 요약, 생성 시각, 만료가 있는 경우 남은 시간이 표시된다. 대기 요청 수는 탭(또는 진입점) 배지로 노출된다. 목록은 화면 진입·포그라운드 복귀·당겨서 새로고침 시 갱신된다.
- **달성 가치**: V10
- **검증 방법**: 요청 3건 생성 → 목록에 최신순 3건 + 배지 3. 하나 승인 → 목록 2건 + 배지 2. 백그라운드에서 신규 요청 생성 후 포그라운드 복귀 → 목록 반영 확인.

### AC6: 요청 상세와 만료 카운트다운
- **설명**: 상세 화면은 `context` 전문, 요청자 이름, `externalId`, 생성 시각, 현재 상태를 보여준다. 만료가 있는 `PENDING` 요청은 남은 시간을 초 단위로 실시간 표시하고, 0에 도달하면 서버 응답을 기다리지 않고 결정 버튼을 비활성화한 뒤 상태를 "만료"로 갱신한다. 이미 처리된 요청의 상세는 결정 결과·처리 시각·처리 방식(수동/자동)을 보여주고 결정 버튼을 표시하지 않는다.
- **달성 가치**: V10
- **검증 방법**: `timeoutSeconds=30` 요청 상세를 열고 카운트다운이 감소하는지, 0 도달 시 버튼이 비활성화되고 "만료"로 바뀌는지 확인. 처리된 요청 상세에 결정 버튼이 없는지 확인.

### AC7: 승인·거절
- **설명**: 상세 화면에서 승인 또는 거절을 선택하면 확인 단계를 거쳐 결정이 확정된다. 결정은 처리자와 처리 시각을 기록하며 되돌릴 수 없다. 이미 처리된 요청(다른 기기·잠금화면 액션에서 먼저 처리된 경우 포함)에 대한 결정은 409로 거부되고, 앱은 현재 상태를 다시 불러와 "이미 처리됨"을 안내한다. 결정은 먼저 도달한 하나만 유효하다(동시 요청 시 두 번째는 409).
- **달성 가치**: V10
- **검증 방법**: 승인 → 확인 → `APPROVED` + 처리자·처리 시각 기록. 확인 단계에서 취소 → 상태 불변. 두 기기에서 거의 동시에 승인·거절 → 하나만 성공, 다른 쪽은 409 + 안내. 처리된 요청에 결정 API 재호출 → 409.

### AC8: 처리 이력
- **설명**: 앱은 사용자 소유의 처리된 요청(`APPROVED` / `REJECTED` / `EXPIRED`)을 처리 시각 역순으로 보여주며, 커서 기반으로 이어서 불러온다. 각 항목은 결과와 함께 **처리 방식**(수동 결정 / 자동 승인 / 자동 거절 / 만료)을 구분해 표시한다. 이력은 삭제되지 않는다.
- **달성 가치**: V10
- **검증 방법**: 수동 승인·자동 거절·만료 요청을 각각 만든 뒤 이력에 세 가지 처리 방식이 구분되어 역순으로 나타나는지 확인. 25건 이상에서 스크롤 시 중복·누락 없이 이어지는지 확인.

### AC9: 자동 응답 모드
- **설명**: 사용자는 설정에서 자동 응답 모드를 `없음` / `자동 승인` / `자동 거절` 중에서 고른다. 자동 모드에서 생성된 요청은 생성 즉시 해당 결과로 처리되고(요청자는 AC3에서 즉시 결과를 받는다), 푸시를 보내지 않으며, 이력에 자동 처리로 기록된다(AC8). 자동 모드가 켜져 있는 동안 대기 목록 상단에 현재 모드를 알리는 배너가 상시 노출되어, 사용자가 통제권을 넘겨 두었다는 사실을 잊지 않게 한다. 모드 변경은 이후 생성되는 요청에만 적용되며 이미 `PENDING`인 요청에는 소급하지 않는다.
- **달성 가치**: V10
- **검증 방법**: 자동 승인으로 바꾼 뒤 생성 → 즉시 `APPROVED` + 푸시 미발송 + 이력 "자동 승인". 배너 노출 확인. `PENDING` 요청이 있는 상태에서 자동 거절로 변경 → 기존 요청은 `PENDING` 유지.

### AC10: 신규 요청 푸시 (APNs)
- **설명**: 자동 모드가 아닌 사용자에게 요청이 생성되면, 백엔드는 PRD-10의 기기 토큰·APNs 경로로 수신자의 모든 등록 기기에 푸시를 보낸다. 푸시 발송은 요청 생성 응답을 지연시키거나 실패시키지 않으며, 무효 토큰은 정리된다. 알림을 탭하면 앱이 해당 요청의 상세(AC6)로 곧바로 진입한다(PRD-10 AC7과 같은 딥링크 라우팅). 알림 탭은 결정을 트리거하지 않는다.
- **달성 가치**: V10
- **검증 방법**: 요청 생성 → 등록 기기에 푸시 도달. APNs 장애를 모사해도 생성 API가 201을 즉시 반환하는지 확인. 알림 탭 → 해당 요청 상세 도달 + 상태 `PENDING` 유지. 앱 미실행 상태에서도 동일하게 동작하는지 확인.

### AC11: 잠금화면 알림 액션
- **설명**: 승인 요청 푸시는 "승인"·"거절" 알림 액션을 제공해 앱을 열지 않고 결정할 수 있게 한다. "승인" 액션은 기기 잠금 해제(Face ID/암호)를 요구한다. "거절"은 안전한 방향의 결정이므로 잠금 상태에서도 실행된다. 액션 처리 결과는 알림 교체(또는 로컬 알림)로 사용자에게 알린다 — 성공 시 결과, 이미 처리됨·만료(409) 시 그 사유. 액션이 네트워크 오류로 실패하면 결정되지 않은 것으로 간주하고 실패를 안내한다(재시도로 결정을 자동 확정하지 않는다).
- **달성 가치**: V10
- **검증 방법**: 잠금 상태에서 "승인" 선택 → 잠금 해제 요구 → 해제 후 `APPROVED`. 잠금 상태에서 "거절" → 잠금 해제 없이 `REJECTED`. 만료된 요청의 알림에서 액션 → 결정되지 않고 "만료됨" 안내. 비행기 모드에서 액션 → 상태 불변 + 실패 안내.

### AC12: 빈·로딩·오류 상태
- **설명**: 대기 목록이 비어 있으면 "대기 중인 승인 요청이 없습니다"와 함께 현재 자동 응답 모드를 보여준다. 로딩 중에는 이전 목록을 유지한 채 진행 표시를 한다. 네트워크·서버 오류는 배너로 알리고 재시도를 제공하며, 오류 중에도 결정 버튼이 결정 성공처럼 보이는 상태로 바뀌지 않는다.
- **달성 가치**: V10
- **검증 방법**: 요청 0건 → 빈 상태 문구 + 모드 표시. 서버 중단 → 오류 배너 + 재시도. 결정 요청 중 서버 중단 → 결정 버튼이 원래 상태로 돌아오고 상태가 바뀌지 않았음을 안내.

## 결정 사항

- **gatekeeper를 별도 서비스로 두지 않고 PocketAide 백엔드·iOS 앱으로 흡수한다.** 인증(OIDC)·푸시(APNs)·기기 토큰을 PRD-10과 공유해 운영 대상을 하나 줄인다.
- **가치는 V9에 편입하지 않고 V10을 신설한다.** 상태 파악(V9)과 결정·통제(V10)는 실패 비용이 다르다. (values.md V10 비고 참조)
- **공개 목록 경로는 옮기지 않는다.** PocketAide는 공용 도메인이므로 gatekeeper의 무인증 `GET /api/requests`를 그대로 옮기면 모든 승인 요청 내용이 외부에 노출된다.
- **만료된 요청은 결정할 수 없다(동작 변경).** gatekeeper는 만료 요청의 승인을 허용했으나, V10의 "침묵이 승인으로 해석되지 않는다"와 충돌하므로 409로 막는다. 이 동작에 의존하는 호출자가 있는지 전환 전에 확인한다.
- **승인 액션만 잠금 해제를 요구한다.** 거절은 자동화를 멈추는 안전한 방향이므로 마찰을 두지 않는다.

## 운영 노트

- 외부 호출자는 API 키 하나를 공유한다(gatekeeper와 동일). 호출자별 키 발급·폐기는 후속 작업이다.
- 기존 gatekeeper `Request.userId`는 gatekeeper 내부 cuid이므로 PocketAide 사용자와 직접 대응되지 않는다. 전환 시 호출자 설정의 수신자 값을 새 식별 방식으로 바꿔야 한다.
- gatekeeper의 Next.js PWA·Web Push·Authelia 연동은 전환 완료 후 폐기한다.

## 열린 질문

- **수신자 식별 방식 (결정 필요)**: 생성 API에서 수신자를 무엇으로 지정할지 — OIDC `sub`, 이메일, 또는 PocketAide가 발급하는 불투명한 수신자 id. 호출자 설정에 개인 식별 정보를 남기지 않으려면 불투명 id가 유리하다.
  - 연관: **수신자 미지정 요청** — 거부(400)할지, 설정된 기본 수신자에게 귀속할지. gatekeeper에서는 미지정이 흔한 호출 형태였을 수 있으므로 기존 호출자 확인 후 결정.
- **기존 호출자 호환 (결정 필요)**: gatekeeper의 경로(`/api/requests`)·필드명·응답 형태를 그대로 유지할지, PocketAide 네임스페이스로 새로 정의하고 호출자를 일괄 수정할지. 전환 기간 동안 gatekeeper 도메인을 어떻게 처리할지(리다이렉트/병행 운영/즉시 종료).
- **기존 데이터 이관**: gatekeeper SQLite의 처리 이력을 PocketAide로 옮길지, 새로 시작할지.
- **알림 본문의 `context` 노출**: gatekeeper는 푸시 본문에 `context` 전문을 넣었다. 잠금화면에 배포 대상·내부 정보가 노출될 수 있다. AC11의 잠금화면 결정을 위해서는 판단 근거가 보여야 하므로, 요약 노출 수준(전문 / 앞부분 / 요청자만)을 결정 필요.
- **앱 내 위치 (결정 필요)**: 8번째 탭으로 둘지, PR 모니터(PRD-10)·세션(PRD-11)과 묶어 "개발" 영역으로 재구성할지. 탭 수가 늘어날수록 하단 탭 바 수용 한계에 닿는다. 결정 후 mockup(`screen-approval-*.html`)을 작성한다.
- **만료 전환 방식**: 관측 시점 판정(lazy)만으로 AC4를 만족할 수 있으나, 만료를 요청자에게 능동적으로 알리거나(웹훅) 만료 직전 리마인드 푸시를 보내려면 백그라운드 스윕이 필요하다.
