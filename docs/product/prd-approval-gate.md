# PRD: 승인 게이트 (gatekeeper 통합)

## 달성 가치
- **V10**: 자동화에 대한 즉시 승인 통제 — CI·배포·에이전트가 사람의 결정을 기다리는 요청을 폰에서 받아 곧바로 승인·거절하고, 기한 안에 결정되지 않은 요청은 명시적으로 만료시켜 침묵이 승인으로 해석되지 않게 한다.

## 개요

별도 서비스로 운영되던 [gatekeeper](https://github.com/dlddu/gatekeeper)(Go 백엔드 + Next.js PWA, Authelia forward-auth, Web Push)를 PocketAide로 흡수한다. 외부 자동화는 사용자가 발급한 호출자 키로 PocketAide 백엔드에 승인 요청을 만들고 결과를 폴링하며, 키 소유자는 iOS 앱에서 APNs 푸시로 요청을 받아 결정한다.

```
외부 자동화 ──(호출자 키)──► pocket-aide 백엔드 ──(APNs)──► iOS 앱
 (CI·에이전트)   요청 생성 / 상태 폴링        │                 대기 목록 · 상세 · 결정
                                             └── OIDC 사용자 ◄── 승인·거절 (OIDC Bearer)
```

이 PRD가 해결하려는 문제는 두 가지다. 첫째, 자동화가 사람의 승인을 기다리는 동안 사용자가 자리에 없으면 작업이 멈춘다. 둘째, 승인 도구가 PocketAide와 별개의 PWA·인증 체계·푸시 채널로 떨어져 있어 알림과 결정 경험이 분산된다.

### 전제 (gatekeeper 레포 확인 결과, 2026-09-29 `762fafe` 기준)

| 항목 | gatekeeper의 현재 동작 | 본 PRD에서의 처리 |
|------|------------------------|------------------|
| 호출자 API | `POST /api/requests`, `GET /api/requests/{id}`, `x-api-key` 헤더 | 새 경로·스키마로 재정의 (아래 "호출자 API 계약") — **호환 없음** |
| 요청 생성 인증 | `x-api-key` 단일 시크릿(환경변수, 모든 호출자 공유) | 호출자별 키로 교체. 앱에서 발급·폐기 (AC1, AC13, AC14) |
| 요청 목록 `GET /api/requests` | **인증 없음**, 전체 요청 반환 | 제거. 목록은 OIDC 뒤의 앱 전용 경로로만 (AC2) |
| 사용자 인증 | Authelia forward-auth (`Remote-User` 헤더) | PocketAide OIDC 미들웨어 (`sub` 기준) |
| 수신 사용자 지정 | 생성 body의 `userId` = gatekeeper 내부 cuid. 생략 가능 | 필드 제거. 요청에 쓰인 호출자 키의 소유자가 수신자 (AC2) |
| 수신자 미지정 요청 | 푸시 없음, 자동 응답 없음, 모든 사용자에게 보임 | 존재하지 않음 — 모든 요청은 키 소유자에게 귀속 |
| 만료 | 조회 시점에만 lazy하게 `EXPIRED` 전환 | 같은 방식(조회 시 판정)을 유지하되 모든 경로에 일관되게 적용 (AC4) |
| 만료 요청 처리 | 승인·거절 처리가 `EXPIRED`를 막지 않음 → **만료된 요청도 승인 가능** | 409로 거부 (AC4) — **동작 변경** |
| 자동 응답 | `NONE` / `AUTO_APPROVE` / `AUTO_REJECT`, 사용자 단위 | 유지 + 자동 처리 여부를 이력에 구분 표시 (AC8, AC9) |
| 푸시 | VAPID Web Push, 본문 = `context` 전문 | 기존 APNs 경로(PRD-10)로 교체, 본문은 키 이름 + `context` 앞부분 (AC10) |
| 결정 UI | 상세 화면 승인/거절 + 확인 다이얼로그 | 유지 (AC7) + 잠금화면 알림 액션 신규 (AC11) |
| 저장소 | SQLite (`User`, `Request`, `PushSubscription`) | PocketAide DB에 새 마이그레이션. 기존 데이터는 이관하지 않음 (운영 노트) |

### 호출자 API 계약

gatekeeper 형식과 호환하지 않고 새로 정의한다. 기존 호출자는 전환 시 클라이언트를 수정한다(운영 노트 "전환 절차").

| 동작 | 경로 | 인증 | 요청 | 응답 |
|------|------|------|------|------|
| 요청 생성 | `POST /api/external/approvals` | `Authorization: Bearer <호출자 키>` | `externalId`(필수), `context`(필수), `requesterName`(선택, 표시용), `timeoutSeconds`(선택) | 201 `{id, status, createdAt, expiresAt}` |
| 결과 조회 | `GET /api/external/approvals/{id}` | 같음 | - | 200 `{id, externalId, status, createdAt, expiresAt, processedAt}` |

- `/api/external/` 아래는 호출자 키만, 그 밖의 `/api/`는 OIDC만 받는다. 인증 경계를 경로로 구분한다.
- 수신자 필드는 없다. 알 수 없는 필드(예: 옛 `userId`)가 오면 400으로 거부해, 옛 클라이언트 설정이 섞여 들어오는 것을 전환 중에 바로 드러낸다.
- `externalId`는 같은 호출자 키 안에서 유일하다(키가 다르면 같은 값을 써도 충돌하지 않는다).
- 상태 값은 gatekeeper와 같은 `PENDING` / `APPROVED` / `REJECTED` / `EXPIRED`를 쓴다.

## 사용자 시나리오 (대표)

1. 점심 중 "승인 요청: prod 배포 v1.42" 푸시 → 알림 탭 → 상세에서 내용과 남은 시간(4분 12초) 확인 → 승인 → 확인 다이얼로그 → CI가 다음 폴링에서 `APPROVED`를 받아 배포를 진행한다.
2. 운전 중이라 결정하지 못함 → 10분 후 요청 만료 → 에이전트는 `EXPIRED`를 받고 중단한다. 나중에 앱을 열면 이력에 "만료"로 남아 있고, 승인 버튼은 없다.
3. 잠금화면에서 알림을 길게 눌러 "거절"을 바로 선택 → 앱을 열지 않고 처리된다. "승인"을 누르면 Face ID로 잠금 해제를 먼저 요구한다.
4. 새 CI 파이프라인을 붙이며 설정에서 "infra-ci" 키를 발급받아 한 번만 보이는 키 원문을 CI 시크릿에 넣는다. 몇 주 뒤 로그에 키가 찍힌 것을 발견하고 앱에서 그 키만 폐기한다 → 다른 호출자는 영향 없이 계속 동작하고, infra-ci만 새 키를 받아 교체한다.
5. 휴가 전 설정에서 자동 응답을 "자동 거절"로 바꿔 둔다 → 대기 탭 상단에 "자동 거절 모드 켜짐" 배너가 상시 보인다 → 복귀 후 이력에서 "자동 거절"로 표시된 요청들을 훑어본다.

## Acceptance Criteria

### AC1: 외부 자동화의 승인 요청 생성 (호출자 키 인증)
- **설명**: 백엔드는 외부 자동화용 요청 생성 엔드포인트를 노출하고, 이를 OIDC와 분리된 호출자 키 미들웨어 뒤에 둔다. 호출자 키는 AC13으로 발급되고 폐기(AC14)되지 않은 키만 유효하며, gatekeeper식 단일 공유 시크릿은 두지 않는다. 요청 형식은 위 "호출자 API 계약"을 따른다. 필수 필드 누락·알 수 없는 필드는 400, 같은 키 안에서 `externalId` 중복은 409, 키 누락·불일치·폐기는 401이다. 호출자 키는 요청 생성(AC1)과 상태 조회(AC3) 두 경로에만 유효하며, 앱용 목록·상세·결정 경로에는 쓸 수 없다. 반대로 OIDC 토큰으로는 요청을 생성할 수 없다.
- **달성 가치**: V10
- **검증 방법**: 유효 키로 생성 → 201 + `PENDING`. 같은 키로 동일 `externalId` 재생성 → 409, 다른 키로는 201. `userId` 필드를 넣어 생성 → 400. 키 없이 → 401. 호출자 키로 앱 목록 경로 호출 → 401. OIDC 토큰으로 생성 경로 호출 → 401.

### AC2: 요청 소유권과 비공개
- **설명**: 모든 요청은 생성에 쓰인 호출자 키의 소유자(AC13) 한 명에게 귀속되며, 호출자가 수신자를 따로 지정하는 방법은 없다. 앱의 목록·상세·결정 경로는 OIDC 인증된 요청자 소유 요청으로 한정되며, 타인 소유 요청 id로의 접근은 존재 여부를 드러내지 않도록 404로 응답한다(PRD-11 AC2와 같은 원칙). 인증 없이 요청 목록이나 내용을 조회할 수 있는 경로는 존재하지 않는다(gatekeeper의 공개 `GET /api/requests`는 옮기지 않는다).
- **달성 가치**: V10
- **검증 방법**: A의 키로 만든 요청이 A의 목록에만 있고 B의 목록에 없는지 확인. B가 A의 요청 id로 상세·승인·거절 시도 → 모두 404. 토큰 없이 목록 경로 호출 → 401. 라우트 목록에 무인증 목록 경로가 없는지 확인.

### AC3: 요청자의 결과 조회 (폴링)
- **설명**: 외부 자동화는 그 요청을 만든 호출자 키로 요청 id의 현재 상태(`PENDING` / `APPROVED` / `REJECTED` / `EXPIRED`), 처리 시각, 만료 시각을 조회할 수 있다. 응답은 AC4의 만료 규칙을 반영한 **실제** 상태여야 한다(만료 시각이 지난 `PENDING`을 `PENDING`으로 돌려주지 않는다). 다른 호출자 키로 만든 요청은 존재 여부를 드러내지 않도록 404로 응답한다. 응답에는 처리자의 OIDC `sub`·이메일 등 사용자 식별 정보를 포함하지 않는다.
- **달성 가치**: V10
- **검증 방법**: 생성 직후 조회 → `PENDING`. 앱에서 승인 후 조회 → `APPROVED` + `processedAt`. `timeoutSeconds=5` 요청을 6초 후 조회 → `EXPIRED`. 키 A로 만든 요청을 키 B로 조회 → 404. 응답 JSON에 사용자 식별자가 없는지 확인.

### AC4: 만료의 일관성
- **설명**: 만료 시각이 지난 `PENDING` 요청은 어떤 경로(요청자 조회, 앱 목록, 앱 상세, 결정 시도)에서 관측되든 `EXPIRED`로 취급된다. 만료된 요청에 대한 승인·거절은 409로 거부되며 상태가 바뀌지 않는다. `timeoutSeconds`가 없는 요청은 만료되지 않는다. 만료된 요청은 대기 목록에서 사라지고 이력(AC8)에 "만료"로 남는다. 만료는 요청을 조회·처리하는 시점에 판정하며, 이를 위한 백그라운드 작업은 두지 않는다(결정 사항).
- **달성 가치**: V10
- **검증 방법**: 만료 시각이 지난 요청에 승인 API 호출 → 409 + 상태 `EXPIRED` 유지(gatekeeper 대비 동작 변경 회귀 테스트). 만료 직후 대기 목록에서 사라지고 이력에 "만료"로 나타나는지 확인. `timeoutSeconds` 없는 요청이 장시간 후에도 `PENDING`인지 확인.

### AC5: 대기 목록
- **설명**: 앱에 승인 요청 대기 목록이 있으며, 사용자 소유의 `PENDING` 요청을 최신순으로 보여준다. 각 항목에는 요청자 이름, `context` 요약, 생성 시각, 만료가 있는 경우 남은 시간이 표시된다. 대기 목록은 하단 탭 바에 항상 보이는 독립 "승인" 탭에 있으며(결정 사항), 대기 요청 수는 이 탭의 배지로 노출된다. 목록은 화면 진입·포그라운드 복귀·당겨서 새로고침 시 갱신된다.
- **달성 가치**: V10
- **검증 방법**: "승인" 탭이 "더 보기"가 아닌 하단 탭 바에 보이는지 확인. 요청 3건 생성 → 목록에 최신순 3건 + 배지 3. 하나 승인 → 목록 2건 + 배지 2. 백그라운드에서 신규 요청 생성 후 포그라운드 복귀 → 목록 반영 확인.

### AC6: 요청 상세와 만료 카운트다운
- **설명**: 상세 화면은 `context` 전문, 요청자 이름, 생성에 쓰인 호출자 키 이름(AC13), `externalId`, 생성 시각, 현재 상태를 보여준다. 만료가 있는 `PENDING` 요청은 남은 시간을 초 단위로 실시간 표시하고, 0에 도달하면 서버 응답을 기다리지 않고 결정 버튼을 비활성화한 뒤 상태를 "만료"로 갱신한다. 이미 처리된 요청의 상세는 결정 결과·처리 시각·처리 방식(수동/자동)을 보여주고 결정 버튼을 표시하지 않는다.
- **달성 가치**: V10
- **검증 방법**: `timeoutSeconds=30` 요청 상세를 열고 카운트다운이 감소하는지, 0 도달 시 버튼이 비활성화되고 "만료"로 바뀌는지 확인. 처리된 요청 상세에 결정 버튼이 없는지 확인.

### AC7: 승인·거절
- **설명**: 상세 화면에서 승인 또는 거절을 선택하면 확인 단계를 거쳐 결정이 확정된다. 결정은 처리자와 처리 시각을 기록하며 되돌릴 수 없다. 이미 처리된 요청(다른 기기·잠금화면 액션에서 먼저 처리된 경우 포함)에 대한 결정은 409로 거부되고, 앱은 현재 상태를 다시 불러와 "이미 처리됨"을 안내한다. 결정은 먼저 도달한 하나만 유효하다(동시 요청 시 두 번째는 409).
- **달성 가치**: V10
- **검증 방법**: 승인 → 확인 → `APPROVED` + 처리자·처리 시각 기록. 확인 단계에서 취소 → 상태 불변. 두 기기에서 거의 동시에 승인·거절 → 하나만 성공, 다른 쪽은 409 + 안내. 처리된 요청에 결정 API 재호출 → 409.

### AC8: 처리 이력
- **설명**: 앱은 사용자 소유의 처리된 요청(`APPROVED` / `REJECTED` / `EXPIRED`)을 처리 시각 역순으로 보여주며, 커서 기반으로 이어서 불러온다. 각 항목은 결과와 함께 **처리 방식**(수동 결정 / 자동 승인 / 자동 거절 / 만료)을 구분해 표시한다. 이력은 삭제되지 않는다.
- **달성 가치**: V10
- **검증 방법**: 수동 승인·자동 거절·만료 요청을 각각 만든 뒤 이력에 세 가지 처리 방식이 구분되어 역순으로 나타나는지 확인. 25건 이상에서 스크롤 시 중복·누락 없이 이어지는지 확인.

### AC9: 자동 응답 모드
- **설명**: 사용자는 설정에서 자동 응답 모드를 `없음` / `자동 승인` / `자동 거절` 중에서 고른다. 자동 모드에서 생성된 요청은 생성 즉시 해당 결과로 처리되고(요청자는 AC3에서 즉시 결과를 받는다), 푸시를 보내지 않으며, 이력에 자동 처리로 기록된다(AC8). 자동 모드가 켜져 있는 동안 대기 목록 상단에 현재 모드를 알리는 배너가 상시 노출되어, 사용자가 통제권을 넘겨 두었다는 사실을 잊지 않게 한다. 모드 변경은 이후 생성되는 요청에만 적용되며 이미 `PENDING`인 요청에는 소급하지 않는다.
- **달성 가치**: V10
- **검증 방법**: 자동 승인으로 바꾼 뒤 생성 → 즉시 `APPROVED` + 푸시 미발송 + 이력 "자동 승인". 배너 노출 확인. `PENDING` 요청이 있는 상태에서 자동 거절로 변경 → 기존 요청은 `PENDING` 유지.

### AC10: 신규 요청 푸시 (APNs)
- **설명**: 자동 모드가 아닌 사용자에게 요청이 생성되면, 백엔드는 PRD-10의 기기 토큰·APNs 경로로 수신자의 모든 등록 기기에 푸시를 보낸다. 알림 제목은 "승인 요청 · {키 이름}"(AC13의 키 이름)이고, 본문은 `context` 앞부분이다. 본문은 APNs 페이로드 한도(4KB) 안에 들도록 잘라내고, 잘렸으면 말줄임(…)으로 표시한다. 잠금화면에서 본문을 가릴지는 iOS "미리보기 표시" 설정에 맡기며 앱이 따로 제어하지 않는다. 푸시 발송은 요청 생성 응답을 지연시키거나 실패시키지 않으며, 무효 토큰은 정리된다. 알림을 탭하면 앱이 해당 요청의 상세(AC6)로 곧바로 진입한다(PRD-10 AC7과 같은 딥링크 라우팅). 알림 탭은 결정을 트리거하지 않는다.
- **달성 가치**: V10
- **검증 방법**: 요청 생성 → 등록 기기에 푸시 도달, 제목에 키 이름 표시. 10KB `context` 요청 → 푸시가 정상 발송되고 본문이 말줄임으로 끝나는지 확인. APNs 장애를 모사해도 생성 API가 201을 즉시 반환하는지 확인. 알림 탭 → 해당 요청 상세 도달 + 상태 `PENDING` 유지. 앱 미실행 상태에서도 동일하게 동작하는지 확인.

### AC11: 잠금화면 알림 액션
- **설명**: 승인 요청 푸시는 "승인"·"거절" 알림 액션을 제공해 앱을 열지 않고 결정할 수 있게 한다. "승인" 액션은 기기 잠금 해제(Face ID/암호)를 요구한다. "거절"은 안전한 방향의 결정이므로 잠금 상태에서도 실행된다. 액션 처리 결과는 알림 교체(또는 로컬 알림)로 사용자에게 알린다 — 성공 시 결과, 이미 처리됨·만료(409) 시 그 사유. 액션이 네트워크 오류로 실패하면 결정되지 않은 것으로 간주하고 실패를 안내한다(재시도로 결정을 자동 확정하지 않는다).
- **달성 가치**: V10
- **검증 방법**: 잠금 상태에서 "승인" 선택 → 잠금 해제 요구 → 해제 후 `APPROVED`. 잠금 상태에서 "거절" → 잠금 해제 없이 `REJECTED`. 만료된 요청의 알림에서 액션 → 결정되지 않고 "만료됨" 안내. 비행기 모드에서 액션 → 상태 불변 + 실패 안내.

### AC12: 빈·로딩·오류 상태
- **설명**: 대기 목록이 비어 있으면 "대기 중인 승인 요청이 없습니다"와 함께 현재 자동 응답 모드를 보여준다. 로딩 중에는 이전 목록을 유지한 채 진행 표시를 한다. 네트워크·서버 오류는 배너로 알리고 재시도를 제공하며, 오류 중에도 결정 버튼이 결정 성공처럼 보이는 상태로 바뀌지 않는다.
- **달성 가치**: V10
- **검증 방법**: 요청 0건 → 빈 상태 문구 + 모드 표시. 서버 중단 → 오류 배너 + 재시도. 결정 요청 중 서버 중단 → 결정 버튼이 원래 상태로 돌아오고 상태가 바뀌지 않았음을 안내.

### AC13: 호출자 키 발급
- **설명**: 사용자는 앱의 승인 게이트 설정에서 호출자 이름(예: `infra-ci`)을 붙여 호출자 키를 발급한다. 키 원문은 발급 직후 한 번만 표시되고 복사할 수 있으며, 서버는 원문을 저장하지 않는다(해시만 저장). 이후 키 목록에서는 이름, 원문 앞부분 몇 글자(식별용), 발급 시각, 마지막 사용 시각만 보인다. 키는 발급한 사용자 소유이며 다른 사용자의 키 목록에 나타나지 않는다. 같은 사용자 안에서 호출자 이름은 유일하다. 키로 생성된 요청에는 그 키가 기록되어, 상세(AC6)·이력(AC8)에서 호출자가 스스로 밝힌 `requesterName`과 별개로 실제 키 이름이 표시된다.
- **달성 가치**: V10
- **검증 방법**: 키 발급 → 원문 1회 표시, 화면을 벗어났다 돌아오면 원문을 다시 볼 수 없음. DB에 원문이 없는지 확인. 발급한 키로 요청 생성 → 201, 목록의 마지막 사용 시각 갱신. `requesterName`을 다른 이름으로 보낸 요청의 상세에 실제 키 이름이 함께 보이는지 확인. 같은 이름으로 재발급 → 거부. 다른 사용자의 키 목록에 보이지 않는지 확인.

### AC14: 호출자 키 폐기
- **설명**: 사용자는 키 목록에서 키를 폐기한다(확인 단계 포함). 폐기는 즉시 적용되어 그 키로의 요청 생성(AC1)과 상태 조회(AC3)가 401이 되며, 되돌릴 수 없다(필요하면 새로 발급한다). 폐기 시점에 그 키로 생성된 `PENDING` 요청은 자동으로 승인·거절되지 않고 대기 목록에 남아 사용자가 직접 결정한다. 이 요청들의 상세와 목록 항목에는 "폐기된 키로 생성됨" 경고가 표시된다. 폐기된 키는 목록에 폐기 시각과 함께 남아, 과거 요청의 출처를 추적할 수 있다. 다른 키는 영향을 받지 않는다.
- **달성 가치**: V10
- **검증 방법**: 키 A·B 발급 → A 폐기 → A로 생성·조회 → 401, B로 생성 → 201. 폐기 전 A로 만든 `PENDING` 요청이 대기 목록에 남아 있고 경고가 표시되는지, 자동 응답 모드(AC9)가 켜져 있어도 상태가 바뀌지 않는지 확인. 폐기 후 이력의 A 요청에 키 이름이 그대로 보이는지 확인.

## 결정 사항

- **gatekeeper를 별도 서비스로 두지 않고 PocketAide 백엔드·iOS 앱으로 흡수한다.** 인증(OIDC)·푸시(APNs)·기기 토큰을 PRD-10과 공유해 운영 대상을 하나 줄인다.
- **가치는 V9에 편입하지 않고 V10을 신설한다.** 맡긴 작업을 받아보는 흐름(V9)과, 자동화가 실행 전에 구하는 허락에 대한 결정(V10)은 실패 비용이 다르다. (values.md V10 비고 참조)
- **공개 목록 경로는 옮기지 않는다.** PocketAide는 공용 도메인이므로 gatekeeper의 무인증 `GET /api/requests`를 그대로 옮기면 모든 승인 요청 내용이 외부에 노출된다.
- **만료된 요청은 결정할 수 없다(동작 변경).** gatekeeper는 만료 요청의 승인을 허용했으나, V10의 "침묵이 승인으로 해석되지 않는다"와 충돌하므로 409로 막는다. 기존 호출자 세 곳(homelab-k3s-mcp, session-platform, pure-agent)은 모두 `EXPIRED`를 받으면 폴링을 멈추므로 이 변경에 영향받지 않는다(2026-09-29 확인).
- **API 키는 호출자별로 발급·폐기한다.** gatekeeper의 단일 공유 시크릿은 하나가 새면 모든 호출자를 교체해야 하고, 어느 호출자가 보낸 요청인지 구분할 수 없다. 호출자별 키로 유출 시 그 키만 폐기하고, 요청 출처를 호출자가 밝힌 이름이 아니라 실제 키로 확인한다(AC13·AC14).
- **폐기된 키의 대기 요청은 자동 처리하지 않는다.** 폐기는 대개 유출 의심 때문이므로 자동 승인은 위험하고, 자동 거절은 정상 요청까지 끊는다. 경고와 함께 사용자 판단에 맡긴다.
- **승인 액션만 잠금 해제를 요구한다.** 거절은 자동화를 멈추는 안전한 방향이므로 마찰을 두지 않는다.
- **수신자는 호출자 키의 소유자다.** 키가 사용자에게 귀속되므로(AC13) 요청에 수신자를 따로 적지 않는다. 수신자를 안 적은 요청이라는 경우 자체가 사라진다. 한 요청을 여러 사람에게 보내야 할 때 확장한다.
- **호출자 API는 gatekeeper와 호환하지 않고 새로 정의한다.** 호출자별 키 도입으로 호출자 설정을 어차피 모두 바꿔야 하므로, 이번에 PocketAide 경로 체계(`/api/external/…`)와 Bearer 인증으로 맞춘다. 대가로 세 호출자 레포의 클라이언트 코드·테스트·배포 설정을 수정한다.
- **gatekeeper는 병행 운영 후 종료한다.** 호출자 레포를 하나씩 옮기며 검증하고, 셋 다 옮긴 것이 확인되면 gatekeeper를 끈다. 전환 기간에는 승인 요청이 PWA와 앱 두 곳으로 나뉜다. homelab-k3s-mcp는 승인 서버에 닿지 못하면 게이트 걸린 쓰기를 거부하므로(fail-closed), 전환이 꼬여도 승인 없이 실행되는 일은 없다.
- **gatekeeper 데이터는 이관하지 않고 종료 시 삭제한다.** 사용자 매핑·이관 비용에 비해 과거 이력의 가치가 낮다. 백업도 남기지 않는다.
- **승인은 하단 탭 바에 보이는 독립 탭으로 둔다.** 대기 개수 배지가 보여야 하므로 "더 보기"에 두지 않고, PR 모니터와 묶지도 않는다. 대신 임시공간 탭을 "더 보기"로 옮긴다(임시공간의 입력은 주로 숏컷·위젯으로 들어온다). 탭 순서는 여정 mockup 작성 시 정한다. 이 이동으로 임시공간 미분류 배지가 하단 탭 바에서 보이지 않게 되는 것은 두 가지로 보완한다: PRD-4 AC5의 배지를 "더 보기" 목록 항목에 표시하도록 개정하고, 위젯에 미분류 개수를 추가한다(PRD-8 AC9).
- **푸시 본문은 키 이름 + `context` 앞부분이다.** 알림만으로 대략 판단할 수 있고 APNs 4KB 한도 안에 들어간다. 잠금화면 노출은 iOS 설정에 맡긴다(AC10).
- **만료는 조회 시점에 판정한다.** 사용자에게 보이는 결과(AC4)는 판정 방식과 무관하므로 가장 단순한 방식을 쓴다. 웹훅·만료 리마인드(후속 작업 1·2)를 도입할 때 백그라운드 정리를 함께 추가한다.
